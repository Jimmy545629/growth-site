## 一、这项任务到底在防什么（先说人话）

一个网站要连后端数据库，中间要「钥匙」。钥匙分两种，**千万不能搞反**：

| 种类 | 长什么样 | 能不能放进网页代码 | 为什么 |
| --- | --- | --- | --- |
| **可发布公开键**（publishable key） | `wbpk_` 开头 | **能**，设计上就该放前端 | 它只说明「我是哪个应用」，本身不带任何权限。真正的权限由服务端按网页来源（Origin）现场判断 |
| **服务端密钥 / 私钥**（secret key） | `service_role`、`sk-` 开头、`eyJ…` 长串、`-----BEGIN PRIVATE KEY-----` | **绝对不能** | 它等于数据库的万能钥匙。网页代码是**公开**的（谁都能右键查看源码），放进去就等于把钥匙贴在大门上 |

所以「密钥排查」查的是**第二种**。查的目标只有一个：**整个仓库（含历史提交）里，第二种钥匙一条都不能有。**

## 二、① 密钥排查（红线优先）

### 2.1 查什么（特征词清单）

这是本次固定的**扫描清单**，覆盖最常见的几种泄露形态：

| # | 特征词 | 对应什么 |
| --- | --- | --- |
| 1 | `service_role` / `serviceRole` / `SUPABASE_SERVICE` / `service[_-]key` | 云服务的**服务端**密钥（最危险的一种） |
| 2 | `sk-[A-Za-z0-9]{16,}` | OpenAI 风格的密钥 |
| 3 | `eyJ[A-Za-z0-9_-]{20,}` | JWT 形状的长串（很多密钥都是这个形状） |
| 4 | `BEGIN [A-Z ]*PRIVATE KEY` | 私钥文件内容（`.pem` 之类） |
| 5 | `wbsk_[A-Za-z0-9]{8,}` | 本项目云服务的**服务端**密钥前缀（`wbpk_` 是公开键，不在此列） |
| 6 | `postgres(ql)?://[^:]+:[^@]+@` | 数据库连接串（里面带账号密码） |
| 7 | `xox[baprs]-` / `AIza[A-Za-z0-9_-]{35}` | Slack / Google 的密钥 |

### 2.2 怎么查（一条可复现的命令）

```bash
git grep -nI -E "service_role|serviceRole|SUPABASE_SERVICE|service[_-]key|sk-[A-Za-z0-9]{16,}|eyJ[A-Za-z0-9_-]{20,}|BEGIN [A-Z ]*PRIVATE KEY|wbsk_[A-Za-z0-9]{8,}|postgres(ql)?://[^:]+:[^@]+@|xox[baprs]-|AIza[A-Za-z0-9_-]{35}" -- .
```

- **为什么用 `git grep` 而不是普通 `grep`**：`git grep` 只搜**仓库真正追踪的文件**，
  自动跳过 `.git/`、`.tmp/`、`node_modules/` 这些不该算的地方，结果才可信。
- **看什么**：正常情况**一行都不该输出**。命令的「退出码」是 `1`（grep 找不到东西时的
  正常返回值），那就代表 **0 条命中**。

### 2.3 结果：0 条

```
$ git ls-files | wc -l
41                                    ← 仓库共 41 个被追踪的文件

$ git grep -nI -E "…上面那条…" -- .
(无输出)
退出码=1                              ← 1 = 0 条命中
```

**历史提交也查了**（有些泄露是「以前提交过、后来删掉」，文件虽然没了，但历史里还在）：

```bash
git log --all -p -S "service_role" --oneline    # 空
git log --all -p -S "PRIVATE KEY" --oneline     # 空
git log --all -p -S "wbsk_"        --oneline    # 空
```

三段都为空 → **不只是现在的代码干净，历史里也从没出现过**。

### 2.4 唯一「像钥匙」的东西，为什么不算泄露

仓库里有 `wbpk_e8u8…`（出现在 `assets/config.js` 和 `db/sync-hot.mjs`）。
它是 **`wbpk_` 开头的「可发布公开键」**（不是 `wbsk_` 开头的服务端密钥）——
只用来表明「我是哪个应用」，**本身不带权限**。放前端是设计上就该如此，**不算泄露**。

> ⚠️ 判断的关键是前缀：`wbpk_` = 可以放前端；`wbsk_` = 绝对不能放（第 5 条特征词就是它）。

### 2.5 结论

**密钥这一项，成果是「把查什么、怎么查固定下来、并跑出 0 条」，不是「修掉一个泄露」。**
仓库本来就是干净的。以后每次上线前，重跑 2.2 那条命令、看到 0 条，即可。

## 三、② `.env` 与忽略规则检查

### 3.1 现状

- 本项目是**纯静态网页**（`index.html` + `assets/*.js`），**根本不需要 `.env` 文件**。
- `.gitignore` 里本来就有 `.env` / `.env.local` 两条 → 「不在仓库 + 被忽略」当时已成立。

### 3.2 检查时发现一个**真实的洞**（已修）

`.gitignore` 原来只有两行：

```
.env
.env.local
```

问题是：**同类的 `.env.production` / `.env.development` / `.env.test` 挡不住**。
实测 `git check-ignore .env.production` 当时返回「不忽略」——也就是说，
将来谁要真建了一个 `.env.production` 并放了密钥，会被**原样提交上去**。

**修法**（`.gitignore`）：两行合并成一条**通配**：

```
.env*
```

一条通配把所有 `.env` 开头的变体**一个不漏**全挡住。若以后真要放一个**不含密钥**的
模板文件（如 `.env.example`），再单独写一行 `!.env.example` 放行即可。

### 3.3 改后证据（可复现）

```bash
$ for f in .env .env.local .env.production .env.development .env.test .env.staging; do
    printf "%-22s " "$f"; git check-ignore -q "$f" && echo "已忽略" || echo "没挡住"; done
.env                   已忽略
.env.local             已忽略
.env.production        已忽略
.env.development       已忽略
.env.test              已忽略
.env.staging           已忽略
```

外加两条「本来就没有」的证明：

```bash
git ls-files | grep -i "\.env"          # 空 → 仓库里没有 .env 文件
find . -maxdepth 2 -name ".env*" -not -path "./.git/*"   # 空 → 本机也没有 .env 文件
git ls-files | grep -iE "\.(pem|key|p12|pfx|keystore|jks)$"  # 空 → 没有私钥类文件
```

**结论：`.env` 不在仓库 ✅、被忽略 ✅，而且现在覆盖了全部 `.env*` 变体 ✅。**

## 四、③ 三类错误提示统一（今天真正要改的代码）

### 4.1 改之前的问题：同一个原因，三套中文

同一个失败原因，页面上有三套不同的中文，分别写在三个地方：

| 出错的地方 | 文案出自哪 | 「云端没连上」那句话长什么样 |
| --- | --- | --- |
| 内容库三列 | `data.js → libraryFail` | 云端组件没加载成功 —— 可能是没联网，也可能网络被拦了…… |
| 首页热搜 | `data.js → hot.fail*` | 云端组件**没有**加载成功 —— 通常是没联网…… |
| 新增/编辑表单 | `cloud.js → CODE_TEXT` | 云端组件没加载成功，稍后再试 |

而且热搜那一处**漏了「连接没建起来」（`no-client`）这一种**，会落到「原因不明」——
明明是连接问题，却说原因不明。

**另外还有一句真的「裸报错」露到用户面前**（`app.js:1481`，今天清单第一问的答案）：

- **改前**：「来源列表没读到 —— 云端可能连不上。…**（query-failed）**」
  ← 括号里是**英文错误码**，等于把内部术语摊给用户看。
- **改后**：「来源列表没读到 —— 这一块暂时不能提交，页面其它部分照常能用。…**（这次没读到云端的内容 —— 可能没联网，也可能只是一时抽风。）**」

### 4.2 改法：把「原因 → 中文」收敛成**唯一一处**

- **`assets/cloud.js`**：把原来的 `CODE_TEXT`（只有写/校验错误码）扩成一张**总表 `FAIL_TEXT`**，
  同时收进读失败的四种原因。读失败时 `readFail()` **直接带上中文 `message`**。
  写接口的大写码（`NO_SDK` / `NO_CLIENT`）用 `FAIL_ALIAS` 指向读接口的小写原因，
  保证「云端没连上」那几句话**只有一份**。
- **`assets/app.js`**：删掉自己的翻译器 `failHint()`；内容包括热搜、表单，
  一律**直接用接口给的 `message`**，不再自己翻中文。
  - 表单那处 `res.reason`（英文）→ `res.message`（中文）——**就是上面那句裸报错**。
  - 热搜那处删掉自己按 `reason` 挑的三句（`failNoSdk` / `failEmpty` / `failQuery`），
    改用 `message`，**顺手补上了漏掉的 `no-client`**。
- **`assets/data.js`**：删掉两套重复中文（`libraryFail` 的 4 句、`hot` 段的 3 句），
  只留**标题 + 标签 + 兜底**。

### 4.3 三类错误的划分（按**出错原因**，不是按页面）

| 类别 | 包含哪几种 | 用户看到的中文（同一原因全站一句） |
| --- | --- | --- |
| **第 1 类 · 连不上** | `no-sdk` / `no-client` | 云端组件没加载成功…… ／ 云端连接没建起来…… |
| **第 2 类 · 云端没给结果** | `query-failed` / `empty` / `WRITE_FAILED` / `PATCH_FAILED` / `DELETE_FAILED` | 这次没读到云端的内容…… ／ 云端还没有这份数据…… ／ 没存进去（改没成功 / 没删掉），稍后再试一次 |
| **第 3 类 · 填得不对** | `MISSING_TITLE` / `TITLE_TOO_LONG` / `MISSING_SOURCE` / `SUMMARY_TOO_LONG` / `BAD_MEDIA` / `DUPLICATE` / `MISSING_ID` | 标题不能为空 ／ 标题太长了…… ／ 请选择一个来源 ／ …… |

### 4.4 怎么证明能用

**（一）纯逻辑验证**（不开浏览器，直接跑真代码 —— 脚本：`2026-10-09` 工作区 `.tmp/verify-day23-rules.mjs`）

```
结果：20 项通过，0 项失败
```

关键几条：
- `no-sdk` 的 `message` 是中文，**不是英文码**；
- 写接口 `NO_SDK` 与读接口 `no-sdk` 是**同一句中文**；
- **热搜的 `no-client` 也有中文了**（旧版会落到「原因不明」）。

**（二）真机验证**（真跑页面、真制造三类错误 —— 脚本：`.tmp/shot-day23-errors.mjs`）

| 场景 | 怎么制造的 | 页面显示（截图图里可见） |
| --- | --- | --- |

| ② 第 2 类 | 拦掉数据面域名 | 「这次没读到云端的内容 —— 可能没联网，也可能只是一时抽风。」 |
| ③ 第 3 类 | 标题留空直接提交 | 「标题不能为空」 |
