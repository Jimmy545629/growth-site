## 一、今日一问：你防了哪一种重复提交或错误输入？怎么测的？

### 一句话答案

**防了两种，而且是两道防线各管一种。**

| 防的东西 | 第一道：页面 | 第二道：数据库 |
| --- | --- | --- |
| **填错**<br>（缺必填 / 超长 / 形态不认识） | `validateEntry()` 当场拦下，给中文提示 | INSERT 策略里的 `WITH CHECK` 再判一遍 |
| **重复提交**<br>（同一来源下标题已经有了） | 提交**前**先查一次，查到就直接回 `DUPLICATE` | `UNIQUE (source_id, title)` 约束，撞上回 `23505` |

**为什么要两道**：

- 页面那道是为了**快** —— 不用等一次网络往返就有中文提示；
- 数据库那道是为了**真** —— 页面代码可以被绕过、可以被改，**表结构不会**。

> ⚠️ 这个分工值得记住：**第一道是体验，第二道才是安全。**
> 只有第一道的接口，等于没有防护。

### 怎么测的（都真跑过，不是「应该没问题」）

| 试的事 | 怎么试的 | 实测结果 |
| --- | --- | --- |
| **空标题** | 清空标题框，点「提交」 | 当场出现「**标题不能为空**」，同时结果区给出 `{"ok":false,"code":"MISSING_TITLE"}`。<br>★ **这一步根本没发网络请求** —— 本地就拦了 |
| **没选来源** | 不选来源，点「提交」 | 「**请选择一个来源**」，`code:"MISSING_SOURCE"`。同样没发请求 |
| **正常提交** | 填好标题 + 来源 + 摘要 + 形态 | `{"ok":true,"id":"u-2026-10-04-2kw","title":"…","source_id":"book-effective-executive","kind":"entry","media":"article","created_at":"2026-10-04T22:08:11.638335+08:00"}` |
| **★ 重复提交** | 把上面那条**原样再交一次** | `{"ok":false,"code":"DUPLICATE","message":"这条内容已经在库里了（同一个来源下标题不能重复）"}` |
| **写库之后** | 用云端 SDK 再查一次 `contents` | 表里**真的多了一行**；总行数 **20 → 21** |
| **伪造留痕**（加练） | 提交时自己塞 `created_via:"admin"` | 被数据库拒：`DATABASE_42501  new row violates row-level security policy for table "contents"` |

**「重复提交」那一条是最值得看的**：它不是「页面记住了你点过」，
而是**真的又发了一次请求、真的又被数据库那层判了一遍** ——
所以换个浏览器、换台机器，同一条还是进不去。

### 三层校验各拦什么（写下来免得以后搞混）

```
用户点「提交」
   │
   ├─ ① 页面：validateEntry()          ← 缺必填、超长、形态不认识 → 中文提示，不打网络
   │
   ├─ ② 接口：先查一次有没有重复        ← 有 → DUPLICATE（中文）
   │        这次查询本身失败 → 不猜，直接放行给下面判
   │
   └─ ③ 数据库：唯一约束 + INSERT 策略   ← 并发撞车 / 伪造字段 → 23505 或 42501
                                      ↑ 这一层才是真正说了算的
```

## 三、几个值得记下来的点

### 1. 「网页能写」这个代价，是先算过才开的

这个项目**不做登录**（PRD 第 2 条），页面用的是**匿名身份**。
所以「网页能写」的准确含义是：**任何打开这个网址的人都能写一条。**

这件事**不是漏想的**，是摊开来算过、然后选择接受：

- 好的一面：你自己在页面上就能加内容，不用再「改 data.js → 找 AI → 提交 → 推送 → 重新发布」；
- 坏的一面：没有登录就没法知道是谁写的 —— 所以**只能靠「把门开小」来控风险**：
  只给 INSERT（不能改、不能删）、字段长度卡死、`kind` 和 `media` 限定取值。

> **一句话**：管不住「谁来写」，就管住「能写成什么样」。

### 2. 空数组 ≠ 成功（这个坑很容易踩）

PostgREST 的写法里，`.select()` 之后如果返回 `data: []`，
意思是「**一行也没动**」，**不是**「悄悄成功了」。

RLS 把写入挡住时，它**不给 error**，只给一个空数组。
代码里当成成功处理，就会出现「页面说存好了、库里什么都没有」——
**这比报一串错还糟**，因为没人会去查。

所以 `insertEntry()` 里专门有一条：

```js
if (!got.length) return fail('WRITE_FAILED', '数据库没有返回写入后的那一行');
```

### 3. 「先查后写」拦不住并发

提交前查一次「有没有重复」，只是为了让提示**准**（一句中文，而不是一串英文错误码）。
它**拦不住**两个人同时提交 —— 两次查询都会说「没有」。

真正的防线是**唯一约束**：数据库在写入那一刻判，晚一步的那次会被顶回来（`23505`），
接口再把 `23505` 翻译成同一句话。

> **教训**：任何「先查一下再写」的逻辑，都要问一句「两个人同时做会怎样」。
> 答案如果是「两个都过」，那就还缺一道数据库层的约束。

### 4. 报错文案会骗人（Day 17 的老结论，今天又用上）

如果哪天在 `WRITE_FAILED` 的细节里看到 **`TypeError: Failed to fetch`**，
**先别怀疑断网** —— 它真实含义往往是服务端的 `403` 或 `42501`，
浏览器**故意不转达**那个错误。

分辨办法：**同一地址，不带 Origin 调一次、带上 Origin 再调一次**，一比就清楚。
