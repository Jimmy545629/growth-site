# Day 17 遗留问题｜接口返回的数据里，哪一项和你建的表对不上？怎么发现的？

> 这篇文章回答的是 Day 17（2026-10-03）的「今日一问」。
> 写于 2026-10-03 深夜。**所有数字都是刚才（23:5x）重新查过的**，不是凭记忆写的。

---

## 一、先用一句话回答

**不是「某一项对不上」，而是「整张表都不在」。**

我建的表叫 `hot_topics`，它被建在了**云应用 A**（`wbapp_B7sQ…`）里；
而网页发布之后，挂的是**云应用 B**（`wbapp_e8u8wx…`）。
网页按配置去 **B** 里找 `hot_topics` —— B 里**根本没有这张表**。

所以「对不上」的不是某一列的数据，是**对象本身找不到了**。
就像你把笔记本放在了二楼书桌，却在三楼书桌上翻，翻不到不是「页码不对」，
是「这本本子不在这张桌子上」。

---

## 二、怎么发现的（这是这条问题的重点）

### 第一步：先别怀疑数据，先确认「表到底在不在」

页面上的表现是「今日热点读不到」。这时候有两种可能：

- 表在，但里面没数据 / 数据不对
- 表压根不在

我第一步做的是**把这两个可能分开**，而不是直接去改查询。做法是在云端跑一次
「列出这个应用里所有的表」：

```
list_tables(应用 B) → 返回的只有 auth / storage / internal 几个系统 schema
```

**我自己建的表，一张都不在。**

这一步就定住了方向：不是数据问题，是**位置问题**。

### 第二步：换个东西再验一次，排除「只是那一张表的问题」

只有一张表不在，可能是建表时手滑。所以我又去查另一张早就存在的表 `sources`
（那是 Day 16 建的，之前一直好好的）：

```
SELECT ... FROM sources  →  42P01 relation "sources" does not exist
```

**`42P01` 就是 PostgreSQL 的「这张表不存在」。**

而 `sources` 明明躺得好好的 —— 在 A 里。到这里就能下结论了：

> **同一个名字，两个库里各有一半。**
> A 里有 `sources`、`contents`、`hot_topics`；B 里什么都没有。

### 第三步：找出「网页到底连的是哪个库」

光知道「有两个库」还不够，得知道**网页实际连的是哪个**。查了两处配置，都是同一个：

| 位置 | 值 |
| --- | --- |
| `assets/config.js` → `cloud.endpoint` | `https://source-board.app.workbuddy.host` |
| `assets/config.js` → `cloud.publishableKey` | `wbpk_e8u8wxL7HunoPn0U8X5CS7_…` |
| `db/sync-hot.mjs` → `PUBLISHABLE_KEY` | `wbpk_e8u8wxL7HunoPn0U8X5CS7_…` |

`wbpk_**e8u8wx**…` 对应应用 **`wbapp_e8u8wx`**。
**网页连的是 B，我的表在 A。** 链条闭合了。

### 第四步：最直接的证据 —— 一个文件里躺着两个同名的应用

最后在 `.workbuddy/applications.yaml` 里看到了病根：

```yaml
applications:
  - name: 大学生成长网站
    locator: wbapp_B7sQFGqRdl7VV5jshqMuIF
  - name: 大学生成长网站
    locator: wbapp_e8u8wxL7HunoPn0U8X5CS7
```

**两个应用，名字一模一样。** 前后建了两次，谁是谁一眼看不出来 ——
这就是整件事的源头。

## 三、为什么这个坑特别难查（值得单独记的一条）

它难查，不是因为原因复杂，是因为**报错信息全部指向了错误的方向**：

### 陷阱 1：浏览器把 403 说成「断网」

服务端实际回的是：

```
HTTP 403 {"error":"access_denied",
          "error_description":"the request origin is not allowed for this client"}
```

**但浏览器不会把这个 403 转给页面。** 页面拿到的统一是
`TypeError: Failed to fetch` —— 这行字的字面意思就是「没连上」，
于是第一反应一定是「网络问题 / 地址写错了」，方向整个偏掉。

### 陷阱 2：curl 是 200，浏览器是失败

更误导的是：我用 `curl` 去打**同一个地址**，返回 **200，数据正常**。

为什么？因为 **curl 默认不带 `Origin` 头**，而服务端是按**来源（Origin）精确匹配**的。
不带来源 → 放行；带了但不在白名单 → 拒绝。

**同一个地址，带不带 Origin 是两种结果。** 不知道这一条，就会在两端来回怀疑自己。

### 陷阱 3：只有真开浏览器才看得见

这个坑**本地怎么测都测不出来** —— 因为它是「网页挂哪个应用」的问题，
只有真的部署上去、用浏览器打开，才会撞上。

> **一句话教训**：**「Failed to fetch」不等于断网。**
> 遇到它，先把「请求本身通不通」和「服务端答不答应」分开验：
> 用 curl 不带 Origin 打一次、带上 Origin 再打一次，两条结果一比，方向立刻就清楚了。

## 五、这道题真正教会我的三件事

1. **「读不到数据」的第一反应，应该是「表在不在」，而不是「数据对不对」。**
   先确认对象存在，再谈内容 —— 顺序错了会把简单问题查成复杂问题。

2. **报错文案会骗人。** `Failed to fetch` 听着像断网，实际是 403 拒绝。
   **永远不要只凭报错的那一句话定方向**，要用能自己控制变量的手段（curl 带/不带 Origin）
   去分离真正的原因。

3. **同名是万恶之源。** 两个应用都叫「大学生成长网站」，靠肉眼看根本分不清。
   **命名要能区分「这一份是干什么用的」**，不然迟早要还这笔债。
   这也正是我加那条「配置改了要确认它属于哪个应用」注释的原因。
