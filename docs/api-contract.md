# api-contract.md —— 接口契约

> **这份文件是什么**：本项目里「页面跟云端之间」说好的那几句话 ——
> **谁**（函数名）、**要什么**（入参）、**给什么**（出参）、**办不成时怎么回话**（错误码 + 中文提示）。
>
> **为什么要有它**：写接口最容易犯的错，是「发出去的形状」和「收回来的形状」
> 两边各写各的 —— 前端以为 `data` 是数组，后端给的是对象；
> 前端以为失败会 `throw`，结果拿到一个 `{error}` 还当成功处理了。
> 把形状**先写下来**，两边都照着它写，就不用靠猜。
>
> 建立于 **Day 18（2026-10-04）**。

## 一、接口一览

| 编号 | 方法 | 函数名 | 作用 | 建在哪 | 建立于 |
| --- | --- | --- | --- | --- | --- |
| **01** | GET | `GROWTH_CLOUD.fetchHotTopics(limit)` | 读「当日热搜」那一份快照 | `assets/cloud.js` | Day 17（**Day 20 补 `updatedAt` 字段**，见一·二） |
| **02** | POST | `GROWTH_CLOUD.postEntry(input)` | **新增一条内容**，写进云端 `contents` 表 | `assets/cloud.js` | **Day 18** |
| **03** | GET | `GROWTH_CLOUD.fetchEntries()` | **读内容库三列的条目**（`contents` 表 `kind='entry'` ＋ 关联 `sources`） | `assets/cloud.js` | **Day 18** |
| **04** | GET | `GROWTH_CLOUD.fetchSources()` | 读来源名单（「新增一条」下拉的选项） | `assets/cloud.js` | **Day 18** |

⚠️ **「建在哪」这一列 Day 19 之后要看仔细**：四条接口**对外的名字没变、一个字段也没变**，
但它们**底下那层**换了文件 —— 见下面这张图。

```
页面 app.js
  ↓ 只调 GROWTH_CLOUD（就是上表这四个名字）
assets/cloud.js   ← 【接口层】校验入参 / 编中文提示 / 编排 / 保证返回形状 == 这份契约
  ↓ 只调 GROWTH_DB
assets/db.js      ← 【数据访问层】等 SDK / 建连接 / 查什么表取哪些列（Day 19 从 cloud.js 拆出来的）
  ↓
云端数据库
```

⚠️ **Day 19 之前，上面两层是一个文件**（都叫 `cloud.js`）。
那天把「查数据库」整段搬去了 `assets/db.js`，`cloud.js` 只留契约这一侧的事。
→ **对调用方（页面）来说，这件事完全看不出来**：接口名字、入参、返回的 JSON 字段，
一个字都没动；`app.js` 那一次**一行都没改**。
（这正是「契约不许动」的意思 —— 搬家不改承诺。）

⚠️ **调用方式**：页面代码一律用官方 SDK，**不许自己手写 `fetch` 去拼 `/.cloud/…` 的地址**，
那样会丢掉 SDK 负责的鉴权和会话管理。SDK 只被 `assets/db.js` 一个文件用。

> ⚠️ 一个**例外要说清楚**：排障时（Day 17 / Day 20）我们用命令行工具
> （`curl` / 一段 Python）**直接打过 `/.cloud/database/rest/…`**。
> 那是**诊断手段**，不是页面代码 —— 目的是「把浏览器的变量一个个摘掉」，好让服务器自己说话。
> **页面里一个字符都不许这么写。**

## 一·二、GET `fetchHotTopics` —— 出参（Day 20 补了 `updatedAt`）

Day 17 建它的时候只承诺了三个字段；Day 20 首页要显示「最后更新」，
于是**新增**一个字段，**老字段一个没动**。

```json
{
  "ok": true,
  "rows": [ /* 这一天要显示的那几条，已按 rank 升序、截到 limit */ ],
  "date": "2026-10-06",
  "updatedAt": "2026-10-06T22:57:31+08:00",
  "total": 30
}
```

| 字段 | 说明 |
| --- | --- |
| `ok` | 恒为 `true`。**页面靠它判断成功，不许靠「没报错」判断** |
| `rows` | 这一天要显示的那几条（已按 `rank` 排、截到 `limit`） |
| `date` | 这份快照是**哪一天**的 → 页面「榜单日期」这一格 |
| `updatedAt` | **Day 20 新增**。这份快照**什么时候抓进云端**的（云端那一行的 `fetched_at`，取这一份里**最晚**的那个时刻）→ 页面「最后更新」这一格 |
| `total` | 库里这一天**一共**几条（**不**被 `limit` 截断，跟 `rows.length` 不是一回事） |

⚠️ **`date` 和 `updatedAt` 是两件事，都要有**：

| | 回答的问题 | 页面上的样子 | 停住时说明什么 |
| --- | --- | --- | --- |
| `date` | 这份数据是**哪一天**的 | 榜单日期：2026-10-06 | 内容本身属于哪天 |
| `updatedAt` | 我们**什么时候**把它抓进来的 | 最后更新：2026-10-06 22:57 | 管道还转不转 |

某天忘了跑同步任务时，**这两个数会一起往后停** —— 那正是这一格存在的理由：
**让「数据几天没更新」一眼就能看出来**，而不是靠人去猜。

⚠️ **兼容性**：这是**新增**字段。已有的调用方（`app.js`）只读它要的那几个，
多一个字段不会影响任何人；`renderHot` 之外的地方一个字没改。

⚠️ `updatedAt` **认不出来时是空串**（`''`），页面**就不画这一格** ——
既不印 `undefined`，也不编一个时间出来（跟 `daysAgo()` 同一个规矩）。

## 一·三、一个**已知但不影响今天**的隐患（Day 20 记录，未改）

`fetchHotTopics` 判「库里最新是哪一天」的方式是：
把云端按 `rank` 升序取回来的**第一行**的 `topic_date` 当成「最新一天」。

⚠️ 问题：**两份快照的 `rank` 都是 1…30**，并列时数据库返回谁在前**没有保证**。
Day 20 实测（连查 6 次）都返回 `2026-10-06`（今天），**这次是对的**，
但那是**行物理顺序**碰巧给的，不是规则保证的。

- **今天为什么不改**：Day 20 的任务边界写明「不改后端 / 数据展示问题记录下来明天处理」，
  而它**当下并不表现为故障**（页面显示的确实是今天的数据）。
- **明天怎么改（建议，未实施）**：把 `assets/db.js` 里那句
  `.order('rank', { ascending: true })` 改成
  `.order('topic_date', { ascending: false }).order('rank', { ascending: true })` ——
  一行改动，`all[0]` 就从「碰巧」变成「**保证**是最新那天的 rank 1」。
  （已实测：这样排序后 `all[0]` 稳定是 `2026-10-06`，且前 3 行同属一天。）

## 二、POST `postEntry` —— 新增一条内容

### 2.1 它做什么

把「内容库」里新的一条内容写进云端数据库的 **`contents`** 表，
**写成功后把数据库里那一行读回来**一起返回。

一句话：**先校验 → 再写入 → 再读回 → 统一形状返回**。

### 2.2 入参（一个对象）

| 字段 | 类型 | 必填 | 限制 | 说明 |
| --- | --- | --- | --- | --- |
| `title` | string | **是** | 去掉首尾空格后 **1～60 字** | 标题 |
| `sourceId` | string | **是** | 必须是 `sources` 表里**已经存在**的 id | 这条内容的出处 |
| `summary` | string | 否 | ≤ 200 字 | 本站提炼的摘要（**不是原文**） |
| `media` | string | 否 | `video` / `article` / `podcast` / `talk`，默认 `article` | 形态 |

⚠️ **`sourceId` 为什么必填**：这是 PRD 硬约束 **C4**（「页面上出现的每一条内容，
都必须能核到原始出处」）在**接口这一层**的落实 —— 没有出处的条目，连库都进不去。

⚠️ **`id` 不用传**：接口自己生成（形如 `u-2026-10-04-2kw`）。
`u-` 前缀是故意的：一眼能看出「这条是页面上加的」，跟种子数据（`book-atomic-habits` 这类）区分开。

### 2.3 出参 —— 成功

```json
{
  "ok": true,
  "id": "u-2026-10-04-2kw",
  "title": "重视贡献：别问「我有多忙」，问「我贡献了什么」",
  "source_id": "book-effective-executive",
  "kind": "entry",
  "media": "article",
  "created_at": "2026-10-04T22:08:11.638335+08:00",
  "row": { }
}
```

| 字段 | 说明 |
| --- | --- |
| `ok` | 恒为 `true`。**页面靠它判断成功，不许靠「没报错」判断** |
| `id` | 数据库里这一行的主键 |
| `title` / `source_id` / `kind` / `media` / `created_at` | **从数据库读回来的真值**，不是把入参抄一遍 |
| `row` | 数据库返回的那一整行原样附上（排查问题时用） |

> ⚠️ `title` 这几项为什么强调「读回来的」：
> 写进去的值和存下来的值**不一定一样** —— 数据库可能做了截断、转换、补默认值。
> **回给页面的必须是库里真实的那个值**，不是我们以为写进去的那个。

### 2.4 出参 —— 失败

```json
{ "ok": false, "code": "DUPLICATE", "message": "这条内容已经在库里了（同一个来源下标题不能重复）" }
```

| 字段 | 说明 |
| --- | --- |
| `ok` | 恒为 `false` |
| `code` | 给代码看的、稳定的英文代号（见下表） |
| `message` | **给用户看的中文**，页面上直接显示这一句 |
| `detail` | 可选。技术细节（数据库原始报错等），**只进控制台，不上页面** |

⚠️ **失败也走 `resolve`，不走 `reject`**。理由：调用方（页面）只需要一个
「成功还是失败」的答案，不需要写 `try/catch`。`throw` 只留给真正的意外 bug。

### 2.5 错误码表（这是这份契约的核心）

| `code` | 什么时候发生 | `message`（页面上就这么显示） | 谁拦下的 |
| --- | --- | --- | --- |
| `MISSING_TITLE` | 标题是空的 / 只有空格 | 标题不能为空 | 页面（本地校验） |
| `TITLE_TOO_LONG` | 标题超过 60 字 | 标题太长了，最多 60 个字 | 页面 + 数据库 |
| `MISSING_SOURCE` | 没选来源 | 请选择一个来源 | 页面（本地校验） |
| `SUMMARY_TOO_LONG` | 摘要超过 200 字 | 摘要太长了，最多 200 个字 | 页面 + 数据库 |
| `BAD_MEDIA` | 形态不是那四种 | 形态不认识，只能是 视频 / 文章 / 播客 / 长访谈 | 页面 + 数据库 |
| **`DUPLICATE`** | **同一个来源下，标题已经存在** | 这条内容已经在库里了（同一个来源下标题不能重复） | 页面先查 + **数据库唯一约束兜底** |
| `WRITE_FAILED` | 云端拒收 / 网络断了 / 其它数据库错误 | 没存进去，稍后再试一次 | 云端 |
| `NO_SDK` | 云端 SDK 没加载出来 | 云端组件没加载成功，稍后再试 | 页面 |
| `NO_CLIENT` | SDK 在但连不上 | 云端连接没建起来，稍后再试 | 页面 |

> ⚠️ **「谁拦下的」这一列值得看**：同一个错误，**页面先拦一次、数据库再拦一次**。
> 页面那次是为了**快**（不用等网络往返就有中文提示）；
> 数据库那次是为了**真**（页面代码可以被绕过、可以被改，表结构不会）。

### 2.6 两个真实会踩的点

**① 报错文案会骗人。**
如果 `WRITE_FAILED` 的 `detail` 里看到 `TypeError: Failed to fetch`，
**先别怀疑断网** —— 这个项目在 Day 17 实测过：它真实含义往往是服务端
`403 access_denied`（请求来源不在白名单），浏览器**故意不转达**那个 403。
分辨办法：**同一地址，curl 不带 Origin（200）vs 带上 Origin（403）**，一比就清楚。

**② 空数组 ≠ 成功。**
PostgREST 的写法里，`.select()` 之后如果返回 `data: []`，
意思是「**一行也没动**」（被 RLS 挡住了或者没找到），**不是**「悄悄成功了」。
所以这个接口把「拿到空数组」当成 `WRITE_FAILED` 处理，绝不假装成功。

### 2.7 服务端留痕：`created_via`

「余力加练」那条要求是「加一条服务端日志，方便以后排查问题」。

**这个项目没有服务器** —— 它是「纯静态网页 + 托管数据库」（约束 C2）。
能「在服务端记一笔」的地方只有一个：**数据库自己**。

做法：给 `contents` 加一列 `created_via`，默认值由数据库填 `current_user`。

| 这一行是谁写的 | `created_via` 里会是 |
| --- | --- |
| 网页上那张表单（匿名身份） | `anon` |
| 维护者通道（管理员 SQL / 脚本） | 管理员角色名 |
| Day 18 之前的旧数据 | 空（这一列是后加的） |

⚠️ **重点不是「加了这一列」，而是它改不了。**
前端提交时要是自己塞一个 `created_via: "admin"`，数据库**当场拒收**：

```
DATABASE_42501   new row violates row-level security policy for table "contents"
```

（原因是 INSERT 策略里有一条 `created_via = current_user` —— 见 `db/schema.sql` 的 Day 18 段。）

**为什么非要「改不了」**：一份能被写的人自己改的记录，等于没有记录。
排查问题时最想看的就是「这一行到底走哪条路来的」；
前端要是能随便填，这句话就没有任何意义。

**实测（Day 18，对着线上真地址跑的）**：

| 试的事 | 结果 |
| --- | --- |
| 提交时自己塞 `created_via: "admin"` | ❌ 被拒 · `42501` |
| 提交时不传 `created_via` | ✅ 写进去 · 数据库记下 `"anon"` |

## 二·二、GET `fetchEntries` —— 读内容库三列的条目

### 2b.1 它做什么

把云端 `contents` 表里 **`kind='entry'`** 的那些行取回来，
**并顺带把每一条的来源（`sources` 表）一起带回来** ——
因为「这条属于哪一栏」这件事存在 `sources.column_key` 上，不在内容本身上。

### 2b.2 入参

无。要几条、怎么分组，都由页面决定。

### 2b.3 出参

```
成功：{ ok: true,  rows: [ {…contents 那一行的字段…, sources: {…}}, … ], total: 13 }
失败：{ ok: false, reason: 'no-sdk' | 'no-client' | 'query-failed' | 'empty' }
```

| 字段 | 说明 |
| --- | --- |
| `rows` | 每一行是 `contents` 的字段 ＋ 一个 `sources` 子对象（`name` / `platform` / `column_key` / `note`） |
| `total` | 一共几条（方便页面核对，不用自己再数一遍） |
| `reason` | 读失败的原因分类，页面按它给出不同的中文说法 |

⚠️ **形状跟 01 / 02 保持一致**：读接口一律 `{ok, reason}`，写接口一律 `{ok, code, message}`。
调用方只要记**两套**形状，不用为每个接口学一种新写法。

⚠️ **这一层只取数、不分组、不做业务判断**：
分组（按 `column_key` 分三栏）、把云端字段还原成页面上要的形状，
都在 `app.js` 的 `buildColumns()` / `entryFromRow()`。
取数的职责只有一件：**把数据原样取回来**
（Day 19 之前这个职责写在 `cloud.js` 里，Day 19 起搬到了 `db.js`；
`cloud.js` 只在取回来之后判「空不空、算不算失败」并换成契约要的形状）。

### 2b.4 `reason` 的四种取值

| `reason` | 什么时候发生 | 页面上显示 |
| --- | --- | --- |
| `no-sdk` | 云端 SDK 没加载出来（多半是没联网 / 被拦） | 「云端组件没加载成功……」 |
| `no-client` | SDK 在，但连接没建起来 | 「云端连接没建起来……」 |
| `query-failed` | 请求发出去了但没拿到结果 | 「这次没读到云端的内容……」 |
| `empty` | 读回来了，但库里一条都没有 | 「云端库里现在一条内容都没有。这不算坏了 —— 是内容还没录进去。」 |

⚠️ **以上四种页面都只做一件事：如实说 + 给「重试」。绝不编内容顶上。**
这一条是 PRD 硬约束 **C4** 的精神，跟「今日热点」读不到时的处理完全一样。

### 2b.5 一个必须记住的取舍：内容库从此**要联网**了

Day 18 之前，内容库读的是**本地 `data.js`**（写死的示例内容），断网照样能看。
改成读云端之后，**断网时这三栏就读不到了**。

这不是 bug，是**知情之后换来的**：

| | 改之前（读本地） | 改之后（读云端） |
| --- | --- | --- |
| 断网 | 照常显示（但内容是死的） | **读不到，如实报错** |
| 页面表单加一条 | 榜单里**看不见**（两处数据各活各的） | **立刻能看见** |
| 内容的份数 | **两份**（本地一份、云端一份） | **一份**（只有云端） |

选它的理由：**同一份内容有两个来源，迟早会出现两种说法** ——
那是这个项目从 Day 10 起就反复吃过的亏（见 `AGENTS.md` 的「一个事实一个来源」）。

⚠️ 边界没变：**个人的打卡 / 收藏 / 自己加的行动项，依然一行都不上云**（约束 C1）。
上云的只有**公开内容**。

## 三、这一版没做的（说清楚，免得以为是漏了）

| 没做的 | 为什么 |
| --- | --- |
| **PATCH（改一条）** | 按 Day 18 清单，属于**第 4 周** |
| **DELETE（删一条）** | 同上 |
| **批量写入** | 按 Day 18 清单，**今天不做**。接口一次只收一条 |
| **登录 / 权限** | PRD 第 2 条明确「不做登录 / 注册 / 账号」 |

⚠️ **代价要说清**：因为不做登录，这个接口**任何人打开网页都能调**。
所以数据库那一侧把权限**限死成只能「新增」** —— 不能改、不能删。
这是「最小开放面」：宁可只开一条窄缝，不开一扇门。

## 四、这份契约对应到代码里的哪几行

| 契约里的东西 | 落在哪（**Day 19 之后**） |
| --- | --- |
| 入参校验 + 中文提示 | `assets/cloud.js` → `validateEntry()`、`CODE_TEXT` |
| 编排：先校验 → 再查重 → 再写入 → 再读回 | `assets/cloud.js` → `postEntry()` |
| 数据库原始错误码 → 契约错误码（23505→`DUPLICATE` 等） | `assets/cloud.js` → `entryWriteFail()` |
| 生成主键（`u-YYYY-MM-DD-xxx`） | `assets/cloud.js` → `makeEntryId()` |
| **读三列条目（含关联来源）** | `assets/cloud.js` → `fetchEntries()` ← 调 `db.js` 的 `selectEntries()` |
| 来源下拉的数据 | `assets/cloud.js` → `fetchSources()` ← 调 `db.js` 的 `selectSources()` |
| 读当日热搜 | `assets/cloud.js` → `fetchHotTopics()` ← 调 `db.js` 的 `selectHotTopics()` |
| **「查数据库」这件事本身**：等 SDK / 建连接 / 表名 / 列名 / 排序 / 条数 / `.insert()` | **`assets/db.js`** → `selectHotTopics()` / `selectEntries()` / `selectSources()` / `selectEntryByTitle()` / `insertContent()` |
