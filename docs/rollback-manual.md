# 回滚手册（Rollback Manual）

> **这份手册回答一个问题：线上出事了，怎么退回去、退多久、退到哪。**
>
> 建立于 **Day 26（2026-10-12）**。当天完成了一次**真实的静态托管回退演练**
> （退回 Day 17 版 → 再恢复 v1.0），全程 **2 分 17 秒**，演练证据在
> [`docs/screenshots/day26/`](screenshots/day26/)。
>
> ⚠️ **本手册只讲「怎么退」，不替你做决定。** 退不退、退到哪一版，
> 由「什么情况必须回滚」（第 5 节判断表）来判。

## 0. 先分清：本项目有几层、哪一层能退

「回滚」在不同系统里指的完全不是一回事。本项目有三层，**能退的和不能退的要分清楚**：

| 层 | 本项目有没有 | 出事了怎么退 | 本手册哪一节 |
| --- | --- | --- | --- |
| **静态托管**（对外网址） | ✅ 有 —— `https://source-board.app.workbuddy.host/` | **能退**：git 移动 HEAD → 重新发布 | 第 3 节（**已实操演练**） |
| **云函数** | ❌ **没有**（Day 21 已核实：本项目没有云函数） | 不适用 | 第 4 节（书面说明） |
| **云端数据库**（内容 / 热搜） | ✅ 有 —— 两张表 `sources` / `contents` ＋ `hot_topics` | **能恢复**：靠 SQL 备份 / 种子重灌 | 第 4 节（**只写不做**） |

**一句话记住**：本项目是**纯静态前端 ＋ 云端只读数据库**。
「网页」和「数据」是**两条独立的命**，回滚要分开想——
退网页不会动数据，改数据也不会影响网页代码。

## 1. 可回退历史（退到哪一版？）

**先看现在有哪些「锚点」**。锚点 = 打了标签的提交，比一串 SHA 好记也好用。

| 锚点 | 指向提交 | 日期 | 是什么 | 用途 |
| --- | --- | --- | --- | --- |
| **`v1.0`** | `698450d` | 2026-10-11（Day 25） | **第一个正式版**（附注标签） | 出事了优先退到这里 |
| `day17-stable` | `39fee88` | 2026-10-03（Day 17） | 项目第一个稳定版 | 退到很旧的干净状态 |

**完整提交链**（`git log --oneline`，越新越靠上）：

```
698450d  Day 25｜产出发布前检查 Skill          ← = v1.0（当前线上）
c8aef80  Day 24 补｜补上发布与线上验证结果
960809c  Day 24｜修掉把「来源名」当「人名」的 Bug
eebb0c0  Day 23｜把失败提示收敛成一处中文总表
4fa60ad  Day 22 补｜修掉验证时抓到的 Promise bug
835a6ec  Day 22｜PATCH / DELETE 上线：增删改查四类操作闭环
5106ecc  Day 21｜第三周验收：逐项对证据，缺项照实说
2b6e6d0  Day 20｜跨域认出问题靠「只留一个变量」
  ...（更早的省略）
39fee88  Day 17｜记下热点的三条后续决定        ← = day17-stable
```

> **⚠️ 一个容易踩的坑（Day 26 实际踩到）**：
> `v1.0` 是**附注标签**（annotated tag，带说明文字），它自己有一个对象 ID（`7bb5183`）。
> 所以 `git rev-parse --short v1.0` 返回的是**标签对象**的 ID，**不是它指向的提交**！
> 要拿它指向的提交，必须写 `git rev-parse --short 'v1.0^{}'`（**花括号逃逸**）→ 才得到 `698450d`。
> `day17-stable` 是轻量标签（lightweight），`git rev-parse` 直接返回提交 `39fee88`，不受影响。

**怎么自己看当前有哪些锚点**：

```bash
cd /d C:\Users\33386\WorkBuddy\growth-site
git tag -l                    # 列全部标签
git log --oneline -10         # 看最近 10 条提交
```

## 2. 回滚前必做的 3 件事（别跳过）

回滚是**把线上的东西换掉**，动手前先确认这三件，否则可能"退了但没退对"：

1. **先弄清线上现在跑的是哪一版。**
   跑 `node skills/pre-release-check/check.mjs --only C1,C2`：
   C2 会告诉你**线上和本地是不是同一份代码**（逐文件比 md5）。
   - 如果 C2 报「不一致」→ 说明线上领先或落后于本地，**先搞清楚状况再动**。
   - 如果 C2 是「N/N 一致」→ 线上 = 本地当前 HEAD，状态干净。

2. **记下当前 HEAD 的 SHA**（回滚就是把它换掉，得知道原来是什么）：
   ```bash
   git rev-parse HEAD
   ```

3. **确认工作区干净**（`git status --short` **没有任何输出**）。
   有未提交的改动时 checkout 会被拦住或带过去 —— **先处理干净再退**。

## 3. ⭐ 静态托管回退路径（本项目的主路径，已实操演练）

### 3.1 为什么是这样退 —— 理解机制比记命令重要

**托管层（`source-board.app.workbuddy.host`）不存版本历史，它只保存「当前这一份」。**
发布只是一次「把本地目录现在的样子覆盖上去」的动作，**平台侧没有「回退按钮」**。

所以「回退」这个动作实际上由两部分拼起来：

```
① 在 git 里把代码退回旧版（本地目录变成旧版的样子）
        +
② 重新发布（把旧的这一份覆盖上去，线上就变旧版了）
        =
   静态托管回退
```

**关键推论**：回退的"按钮"在 **git**，不在托管平台。你退到哪个提交，线上就是哪个提交的样子。

### 3.2 完整操作步骤（Day 26 实测走通）

```bash
# ① 退到目标锚点（比如退回 day17-stable）
cd /d C:\Users\33386\WorkBuddy\growth-site
git checkout day17-stable
#   → 会提示进入 "detached HEAD" 状态，这是正常的：
#     detached HEAD = HEAD 不指向任何分支，而是直接指向某个提交。
#     在这个状态下改文件、提交都安全，随时可以 git checkout main 回到主线。

# ② 确认退对了（HEAD 应等于目标提交）
git rev-parse --short HEAD
git ls-files | wc -l          # 文件数会变（Day 17 版是 27 个）

# ③ 重新发布 —— 让线上也变成旧版
#    本项目「发布」= 把当前目录同步到线上；这里由 AI 调「发布为应用」完成。
#    （纯手动场景下，等价于把当前目录重新上传到托管平台。）

# ④ 验证线上真的退回去了
node ~/.workbuddy/skills/pre-release-check/check.mjs --root . --only C1,C2
#   → C1 应 HTTP 200（线上还活着）
#   → C2 应「线上与本地一致」（说明线上跑的就是你刚 checkout 的旧版）
```

### 3.3 恢复（把新版退回线上）

```bash
# ⑤ 回到主线（v1.0）
git checkout main

# ⑥ 确认回来了
git rev-parse --short HEAD     # 应 = 698450d
git ls-files | wc -l           # 应 = 50

# ⑦ 重新发布 —— 线上恢复成 v1.0

# ⑧ 验证恢复
node skills/pre-release-check/check.mjs --only C1,C2
#   → C2 应「11/11 一致」
```

### 3.4 Day 26 实测记录（真实耗时）

| --- | --- | --- | --- |
| 开始 | 记录起点 | 22:08:56 | — |
| ① | `git checkout day17-stable` | 22:09:12 → 22:09:16 | **4 秒** |
| ② | 确认 HEAD / 文件数 | 22:09:16 | 计入上一步 |
| ③ | 重新发布（旧版） | 22:09:22 起 | — |

| ⑤ | `git checkout main` | 22:10:23 → 22:10:27 | **4 秒** |
| ⑦ | 重新发布（v1.0） | 22:10:32 起 | — |

**结论**：**整条静态托管回退路径，从决定退到线上恢复，实测 2 分 17 秒。**
其中真正的「危险窗口」（线上处于旧版、内容不对的时间）只有约 **1 分钟**。

> **验证要点（怎么证明"真退了"而不是"以为退了"）**：
> - **文件数会变**：v1.0 是 50 个文件，Day 17 版是 27 个 —— 数字对不上就是没退对。
> - **C2 的比对文件数会变**：v1.0 比对 11 个文件，Day 17 版比对 8 个
>   （旧版没引用 `db.js` / `hero-video.css` 这些 Day 18 之后才有的文件）。
> - **旧版可能"功能缺失"是正常的**：回退后线上是 Day 17 版，
>   它不知道 Day 18 之后云端表结构的变化 —— 实测当时「今日热点」显示「这次没读到」。
>   **这不是回退失败，恰恰证明回退真的生效了**（新版才有那套完善的数据读取）。

## 4. 云函数回退与数据恢复（本项目**不做实操**，只备查）

> ⚠️ **为什么不做实操**：Day 21 已核实，**本项目没有云函数**（那三样"云函数/检查台/健康接口"
> 本项目都没有）。没有的东西没法演练。所以这一节是**书面预案**，真到那一天再照做。
> **数据恢复**涉及真实的云端数据，**风险高、不可逆**，只作为预案记录，不在演练中执行。

### 4.1 云函数回退 —— 本项目不适用

本项目是**纯静态前端**，页面上所有的"逻辑"都在 `assets/*.js` 里跑，
**没有部署任何服务端函数**。所以：

- **不存在"云函数版本回退"这件事** —— 没有云函数可退。
- 如果**将来**加了云函数（比如把 `db/sync-hot.mjs` 搬上云、或加一个写入接口），
  那才需要在本手册补一节，做法是：**每次部署云函数前先记下版本号 → 出事时在控制台
  选回上一个版本**（云函数平台通常保留历史版本，支持一键回滚）。
- **补救**：如果哪天不小心把云函数改坏了，第一选择是**回到上一个已部署版本**；
  实在不行，把函数代码从 git 历史里 checkout 出来重新部署。

### 4.2 数据恢复 —— 真实需要，但目前靠"可重灌"

云端数据库里有两类数据，**恢复策略不同**：

| 数据 | 表 | 丢了要紧吗 | 怎么恢复 |
| --- | --- | --- | --- |
| **收录内容**（语录/访谈/政策） | `contents` | **要紧** —— 正式收录是手工摘录的，丢了要重摘 | 无自动备份；依赖 Jimmy 手工摘录记录（在 CHANGELOG / docs 里有留存） |
| **来源列表** | `sources` | 一般 —— 就那几个来源 | `db/seed.sql` 可重新灌入 |
| **热搜快照** | `hot_topics` | **不要紧** —— 是自动抓取的公开数据 | 跑 `db/sync-hot.mjs` 重新抓一次即可 |

**⚠️ 现状的诚实结论（Day 26）**：

- 本项目**没有任何自动数据库备份**。托管方案里也没有开定时快照。
- **能重灌的**：`sources`（`seed.sql`）、`hot_topics`（重跑同步）。
- **不能重灌的**：`contents` 里**手工摘录的富字段**（金句/行动点/启示/技能）——
  这些只存在于云端那一份，**丢了就是丢了**。目前只能靠 `docs/` 里的摘录记录人工复原。
- **⚠️ 这是一条真实的风险**，也是"以后要做"的待办：
  **给 `contents` 加一个定期导出**（哪怕一周手动导一次 CSV），
  或者把每次新增内容同时在 `docs/` 里留一份可复原的文字记录。

**真要恢复数据时的做法（预案）**：

```sql
-- ① 先看清现在有什么（只读，安全）
--    （用 AI 的云端数据库工具查，或走「设置—数据管理—应用」的控制台逐行看）
SELECT count(*) FROM contents;

-- ② 如果是"误删了几行"：从 docs/ 的摘录记录里找回原文，重新 POST 一条
--    （内容库页面上就能加，不用写 SQL）

-- ③ 如果是"整表没了"：先重灌能重灌的
--    sources  → 重跑 db/seed.sql
--    hot_topics → 重跑 db/sync-hot.mjs
--    contents → 只能靠手工摘录记录人工补
```

> **⚠️ 恢复数据前，先把当前状态导出留底**（哪怕截个图），
> 否则"恢复"本身可能把仅剩的好数据也弄没。**不可逆操作永远先备份。**

## 5. ⭐ 什么情况必须回滚（判断表）

**这张表回答"该不该退"**。回滚是有代价的（用户会看到旧版），所以不是"一出问题就退"。

### 5.1 判断总原则

> **先问一句：这个问题"退回去"能不能解决？**
> 能解决 → 才轮到考虑回滚。
> 不能解决（比如数据丢了、云端挂了）→ 回滚没用，去看第 4 节。

### 5.2 判断表

| # | 情况 | 严重度 | 必须回滚？ | 为什么 / 怎么做 |
| --- | --- | --- | --- | --- |
| 1 | **线上打不开 / 白屏 / 整个页面崩了** | 🔴 致命 | **必须** | 用户完全用不了。立刻退到上一个锚点（`git checkout v1.0` → 重新发布）。 |
| 2 | **核心操作坏了**（打卡点不动、收藏丢、内容库读不出） | 🔴 致命 | **必须** | 功能不可用。退。**先确认是代码问题**（本地也复现）再退。 |
| 3 | **数据被写坏**（页面上显示明显的错误内容、错别字进了正式收录） | 🟠 严重 | **看情况** | 如果只是**某几条数据错** → **别退代码**，改数据就行（内容库能编辑）。如果是**代码导致所有数据都显示错** → 退。 |
| 4 | **样式崩了**（错位、颜色乱、字体全变） | 🟡 一般 | **看情况** | 页面还能用的话，**不一定退** —— 可以先热修（改一行重新发布，见 5.3）。 |
| 5 | **只是某个小功能不好用**（按钮位置别扭、文案不通顺） | 🟢 轻微 | **不必须** | 不影响使用，**记下来下次一起改**，别为这个回滚。 |
| 6 | **线上加载慢 / 偶尔抖一下** | 🟡 一般 | **不必须** | 先观察是不是网络抖动。**别急着退**（退了大概率也一样慢）。 |
| 7 | **云端数据库连不上**（页面提示"没读到"） | 🟠 严重 | **❌ 退没用** | 这是**数据层**的问题，退网页代码解决不了。去查云服务 / 网络。 |
| 8 | **数据丢了（内容被删）** | 🔴 致命 | **❌ 退没用** | 回滚代码不会把数据带回来。走第 4.2 节的数据恢复。 |
| 9 | **只是你自己看着不顺眼，用户没报问题** | 🟢 轻微 | **不必须** | 回滚是"救火"不是"装修"。留着，改天正常发布。 |
| 10 | **刚发布完，立刻发现漏了一处** | 🟠 严重 | **看情况** | 如果这处**影响使用** → 退（比"等着改完再发"快）。如果**只影响观感** → 直接热修更快。 |

### 5.3 「回滚」还是「热修」？—— 先算这道题

不是所有问题都值得回滚。**回滚 = 退回旧版**（要重新发布一次，线上短暂变旧），
**热修 = 就地改一行再发布**（线上始终是新版，只是修好了）。

> **判断口诀**：
> **改得动、改得快（一行以内）→ 热修。**（比回滚少一次往返，用户几乎无感）
> **改不动、或改起来有风险（要动好几处、或怕改出新问题）→ 回滚。**（退回已知能用的版本最稳）
> **分不清哪个更安全 → 回滚。**（"已知能用"永远比"改了一半"强）

### 5.4 决定回滚后的动作顺序

```
① 先别慌改东西 —— 记下现在线上的状况（截图 / 记 SHA）
② 确认退到哪一版（一般是 v1.0；不确定就退最近一个能用的锚点）
③ 按第 3 节走：checkout → 重新发布 → 验证
④ 退回后**立刻验证**：C1（线上活着）+ C2（线上=你退的那版）+ 人工看一眼页面
⑤ 通知用户："线上出问题，已退回稳定版，正在修"
⑥ 修好后，从主线重新发布，恢复
```

## 6. 演练的结论：真出事敢不敢用这套流程？

**Day 26 演练回答**：

- **敢。** 整条路径 **2 分 17 秒** 走通，其中危险窗口只有约 1 分钟。
- **靠得住的地方**：git 锚点（`v1.0` / `day17-stable`）让"退到哪"没有歧义；
  C2 检查让"退没退对"有**数字证据**（不是靠感觉）。
- **要小心的地方**：
  1. **回退不影响数据** —— 网页退回去了，云端数据该怎样还怎样（反之亦然）。
  2. **旧版可能有"功能缺失"** —— 退到很旧的版本时，它可能不认识当前的云端结构
     （实测 Day 17 版读不出热点）。**退得越远，越可能"能打开但功能不对"**。
  3. **本次只演练了"代码回退"** —— 数据恢复**没有演练**（见第 4 节，风险太高，只备查）。

> **下一步（余力加练之外的建议）**：
> 给 `contents` 表加一次**手动导出**（把手工摘录的富字段存一份到 `docs/`），
> 这是目前**唯一没有兜底**的地方。
