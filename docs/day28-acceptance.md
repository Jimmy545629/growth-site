### 2. 那个「红灯」：云端写入被拒 —— 是设计，不是故障

实跑第 8 步试着写一条测试数据，云端返回：

```
DATABASE_42501  permission denied for table contents
```

**这不是 bug。** 查证过程：

1. `docs/CHANGELOG.md` 5.2 节记着 **Day 27 晚执行了「路线A」**：
   「收回写权限 ＋ 撤掉页面写入口，**两道门一起关**」，当天他回了一个字「收」。
2. 云端现状用管理通道核过：
   - 三张表 `contents` / `hot_topics` / `sources` 的 RLS 策略**只有 SELECT**（三条 `*_read_all`）；
   - 没有任何 INSERT / UPDATE / DELETE 策略。
3. 也就是说：**网页那侧只有读权限**，这份「写不进去」正是要的结果。

> 产品现在的形态是：**内容只读（由助手代写进库）＋ 个人记录存本地**。
> 所以「一次线上写入」这条验收要求，在本作品上对应的是
> **打卡 / 收藏写入后刷新仍在**（A-3 / A-4 已证），而不是「网页能往云端写」。

#### P-1 的根因（已定位到行，但**今天没动代码**）

| 文件:行 | 现在的写法 | 问题 |
| --- | --- | --- |
| `assets/db.js:159` | `.order('rank', { ascending: true }).limit(400)` | **只按 rank 排，没按日期排**。库里 4 天每天都有 rank=1，谁排第一由数据库决定 —— 实测拿到的是 **10-03** |
| `assets/cloud.js:108` | `var latest = String(all[0].topic_date)` | 注释写的是「取库里**最新那一天**」，但 `all[0]` 并不是最新那天 |

**为什么以前没暴露**：Day 17 建表时库里只有一天的数据，`all[0]` 天然就是那一天。
**是哪天开始坏的**：库里出现第 2 天快照的那天起（10-06）。

**云端 hot_topics 实况**（用管理通道查的）：

| 榜单日期 | 条数 | 最后抓取时间 |
| --- | --- | --- |
| **2026-10-15** | 30 | **2026-10-15 22:34:21** ← 最新 |
| 2026-10-13 | 30 | 2026-10-13 22:14:18 |
| 2026-10-06 | 30 | 2026-10-06 22:57:28 |
| 2026-10-03 | 30 | 2026-10-03 16:20:51 ← 页面现在读的是这批 |

**修法（候选，未执行）**：

- **甲**：`db.js` 排序加一句 `.order('topic_date', { ascending: false })`，排在 `rank` 前面；
- **乙**：`cloud.js` 不赖排序，改成从 `all` 里自己算**最大的那个日期**（更稳，不怕后端排序变）。

**我的建议是「乙」**：甲依赖后端的排序语义，乙是就地算出来，跟项目里
「同一个事实只允许有一个来源、能现算就现算」那条规矩一致。两处一起做也行。

### 2.2 人工查：还有没有「写死的数」

Day 27 一口气修掉过 4 处同类病（「今天 08:00」「12 条」「示例内容」「5 本书名单」）。
今天顺着这条线再扫一遍，**又抓到 4 处**（1 处同类病残留、1 处运维真相、1 处代码重复、**1 处文档与线上不符**）。

#### R-1｜页面上还剩**唯一一处**写死的数字：「更新节奏 · 每天 08:00」

`assets/data.js:73`：

```js
{ label: '更新节奏', value: '每天', unit: '08:00', note: '只推精选，不做搬运' }
```

这是三张统计卡里**唯一一张还写着死值的** —— 另外两张（「内容库收录」「今日行动」）
Day 27 都改成现算了（`from: 'library'` / `from: 'actions'`），只有这张漏在改写之外。

**它跟 P-1 叠在一起，观感最差**：访客同一屏里看到
「更新节奏：每天 08:00」＋「榜单日期：2026-10-03」，两句互相打脸。

#### R-2｜自动化任务设的是 08:00，但**从来没有一次在 08:00 跑成过**

用自动化清单核过：任务名「每日更新『今日热点』快照」，状态 `ACTIVE`，
频率 `FREQ=DAILY;BYHOUR=8;BYMINUTE=0` —— 确实设的是每天 08:00。

但云端表里的**执行历史只有两次，都在晚上**：

| 榜单日期 | 写库时间 |
| --- | --- |
| 2026-10-13 | 22:14 |
| 2026-10-15 | 22:34 |

**说明什么**：定时任务要靠「到点时电脑开着、WorkBuddy 在跑」才能触发；
他到点多半没开机，所以两次都是晚上开工时补上的。
→ **页面上那句「每天 08:00」是一个没有兑现过的承诺。**
（这正是今天「余力加练」里说的「部署日志提醒」想解决的事 —— 但今天不动。）

#### R-3｜同一件事有两份实现：「拼本地日期」

| 文件:行 | 函数 | 写法 |
| --- | --- | --- |
| `assets/rules.js:36` | `dayKey(date)` | 用 `pad2()` 拼 `YYYY-MM-DD` |
| `assets/cloud.js:519` | `localDate()` | 自己内联了一个 `p()`，拼同一串 |

两份干的是**同一件事**（按本地时间拼日期串），违反「同一个事实只允许有一个来源」。

**但它是有理由的**：`rules.js` 在 `cloud.js` **之后**加载（见 `index.html` 的顺序），
`cloud.js` 文件头拿不到 `window.GROWTH_RULES`（Day 27 那段注释记过这个坑）。
→ **判定：保留，但在文档里记一笔**。真要合并，得先动加载顺序，影响面大，不该在结营当天动。

#### R-5｜`README.md` 里有两处说法**跟线上对不上**（同一件事两个版本）

| 位置 | README 的说法 | 线上实际 |
| --- | --- | --- |
| `README.md`「还没有的」第 1 条 | 「**没有搜索**、没有登录（这是有意不做）」 | **Day 27 已经加了「筛选 ＋ 搜索」**（当时是 Jimmy 当场的决定，覆盖了那条非目标） |
| `README.md`「还没有的」第 2 条 | 「内容全是**示例**」＋「『今日一篇』同样是示例内容，卡片上带着『示例内容』标记」 | **Day 27 已经把「示例内容」标记摘掉了** —— 因为它自己变成了一句假话；库里现在是 16 条带真实出处的真内容 |

**这类「文档说谎」比没有这句话更糟** —— 一个照着 README 去验收的人，会得出和线上完全相反的结论。

**处理**：这两处**已就地修正**（`README.md` 里加了 `⚠️ Day 28 更正`，原文用删除线留档）。
理由：README 是**交付物**，交付给别人的东西不能自相矛盾；而按 `AGENTS.md` 第 5 条，
改文档**「只许追加和修正，不许推倒重写」** —— 这次是修正，且原文保留。

#### R-4｜正面结论：Day 27 修的那 4 处，一处都没复发

- 「今天 08:00」（顶栏那句）→ 现在改成现算「内容更新于 N 天前」✅
- 「12 条」（统计卡）→ 现在现算 16 条 ✅
- 「示例内容」标注 → 已摘掉 ✅
- 「5 本书名单」（底部来源）→ 现在从库里去重现算，13 家 ✅

文档与代码一致性也核了：`AGENTS.md` 说「代码文件共 11 个」，实际 `ls` 数出来 **11 个** ✅。

### 2.3 板块小结论

**没有「同一个数字在页面上有两个来源」的活 bug**（Day 27 已经清干净了）。
剩下的四类是：**一处写死文案（R-1）、一处没兑现的承诺（R-2）、一处有理由的重复（R-3）、
一处文档与线上不符（R-5）**。

处理方式分两种：

| 项 | 怎么处理的 | 为什么 |
| --- | --- | --- |
| **R-5**（文档不符） | ✅ **已就地修正** | README 是**交付物**，不能自相矛盾；按第 5 条「只许追加和修正」，原文用删除线留档 |
| R-1 / R-2 / R-3 | ⬜ **只记录，没动手** | R-1/R-2 要改页面文案 ＋ 涉及「承诺要不要兑现」的判断；R-3 要动脚本加载顺序 —— **都不该在结营当天自己决定** |
