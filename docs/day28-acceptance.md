### 修 1｜首页「今日热点」显示的是 12 天前的榜单

**现象**：页面标「榜单日期：2026-10-03」，而云端 `hot_topics` 里**今天 22:34 刚写了 30 条**。

**根因（两行，互为因果）**：

| 文件:行 | 原来的写法 | 问题 |
| --- | --- | --- |
| `assets/db.js` `selectHotTopics()` | `.order('rank', { ascending: true }).limit(400)` | **只按 rank 排、没按日期排**。库里每天都有 rank=1，谁排第一由数据库决定 |
| `assets/cloud.js` `fetchHotTopics()` | `var latest = String(all[0].topic_date).slice(0,10)` | 注释写「取库里**最新那一天**」，但 `all[0]` 并不是 |

Day 17 建表时库里只有一天数据，`all[0]` 天然就是那一天；库里出现第 2 天快照（10-06）之后开始坏。

**改法（两处都改，互为双保险）**：

1. `db.js` 补一句 `.order('topic_date', { ascending: false })`，排在 `rank` 前面；
2. `cloud.js` 不赖排序，**从拿回来的所有行里自己算最大的那个日期**。

**验证（在线上页面里用真实云端数据跑，不靠推断）**：

| 测什么 | 结果 |
| --- | --- |
| 库里总行数 | 120（4 天 × 30 条） |
| 旧方式（取第一行） | `2026-10-03` ← **bug 复现** |
| 新排序（取第一行） | `2026-10-15` ✅ |
| 新逻辑（自己算最大日期）·对旧排序数据 | `2026-10-15` ✅ |
| 新逻辑（自己算最大日期）·对新排序数据 | `2026-10-15` ✅ |
| 新排序前 4 行 | 2026-10-15 / rank 1,2,3,4 ✅ 顺序正确 |
| 查询报错 | 无 |

脚本：当天工作区 `.tmp/verify-day28-fix.mjs`

### 修 2｜统计卡「更新节奏 · 每天 08:00」是一个没兑现过的承诺

`assets/data.js` 的 `stats` 第三张原来写死 `{ value: '每天', unit: '08:00' }`，
是三张卡里**唯一还写死值的**（另两张 Day 27 已改成现算）。

而定时任务虽然设的就是 `FREQ=DAILY;BYHOUR=8`（状态 ACTIVE），
**两次成功执行都在晚上 22 点**（10-13 22:14、10-15 22:34）—— 它得靠「到点时电脑开着」才跑得成。

**改法**：把具体钟点去掉，`unit` 由 `'08:00'` 改成 `'更新'`（页面上显示「每天 更新」）。
每天确实会抓一批（时间不定），这句话站得住；手头这份数据是哪一天的，「今日热点」那块另有如实标注。

## 二、核心流程重复检测（板块 ②）

**训练营原文**：「完整走两遍『**写入 → 刷新 → 持久化 → 修改 → 删除**』，两遍结果一致 = 可重复完成。」

**本项目的「核心记录」**＝打卡（`growth-site.checkins.v1`）＋收藏（`growth-site.favorites.v1`），都存浏览器本地。

**两遍各开一个全新的浏览器档案**（两个互不相干的实例），每遍都完整走五步，逐步取存储快照。

> 换成独立档案后才是真正的「独立复现」。这个教训值得记：**检测方法本身也要被检测。**

**结果：8 个观测点逐字节完全一致 ✅**

## 四、「能继续改」检测（板块 ④）

**训练营原文**：「让 AI（或同伴）**只看仓库和文档**，回答：『如果要给你的核心记录加一个统计功能
（打卡应用对应「统计完成率」），从哪张表、哪个接口开始改？』它能给出合理路径 = 架构和文档足够清楚。」

**做法**：派一个**独立上下文的 AI**，只给它仓库目录，不给任何背景解释。
问题原样照抄，一字未改。

**它的回答（摘要）**：

- **先纠正了问题的假设**：「这个项目里，核心记录**既不在数据库表里，也不走任何接口**」——
  打卡存在 `localStorage['growth-site.checkins.v1']`，依据是 `db/schema.sql` 第 25–28 行
  和 `PRD.md` 硬约束 C3（数据只存在用户自己浏览器里，不做登录）。
- **改动路径**：`assets/rules.js` 加纯函数（算）→ `assets/data.js` 加文案（不写死数字）→
  `assets/app.js` 画（`renderStats()` 加一个 `from` 分支）→ 打勾后顺手重画。
- **为什么这样分层**：直接引用了 `AGENTS.md` 第 4 条「文件分工」原文
  「`rules.js` 所有『算』的逻辑（日期、连续天数、**完成度**；纯函数，不碰存储和页面）」
  和第 3 条「涉及『算』的（连续天数、完成度），要在命令行里把规则单独跑一遍」。
- **主动列出 7 处「看起来该改、其实不该动」**：不要给 `schema.sql` 加打卡表；
  不要动 `db.js` / `cloud.js`；不要往 `store.js` 塞统计；`data.js` 的 `actions[].done` 绝对不要再出现
  （Day 10 的教训）；不要改 `storeKey` 的名字；不要在 `stats` 里写死数字；不要用 `innerHTML` 拼百分比。
- **结论**：「**能，而且路径相当清楚**……技术路径清楚到可以立刻动手。
  **缺的不是能力，是一个还没定的定义**」—— 「完成率」的时间窗口、分母口径在 `PRD.md` 里还没定，
  而按仓库自己的规矩（`AGENTS.md` 第 2 条），加新功能前必须先问过作者、登记进 PRD。

**判定**：✅ **通过**。它只看仓库和文档就给出了合理路径，还准确指出了「产品口径未定」这个真实缺口 ——
说明**架构和文档确实足够清楚，作品真的能继续改**。
