### 四、★ 检测抓出一个真 Bug：首页「今日热点」显示的是 12 天前的榜单

**现象**：线上首页「今日热点」头部写着「榜单日期：2026-10-03 · 最后更新：2026-10-03 16:20」，
而云端库里**今天 22:34 刚抓了 30 条最新的**：

| 榜单日期 | 条数 | 最后抓取 |
| --- | --- | --- |
| **2026-10-15** | 30 | **2026-10-15 22:34:21** |
| 2026-10-13 | 30 | 2026-10-13 22:14:18 |
| 2026-10-06 | 30 | 2026-10-06 22:57:28 |
| 2026-10-03 | 30 | 2026-10-03 16:20:51 ← 页面读的是这批 |

**根因（已定位到行）**：

| 文件:行 | 现在的写法 | 问题 |
| --- | --- | --- |
| `assets/db.js:159` | `.order('rank', { ascending: true }).limit(400)` | **只按 rank 排、没按日期排**；库里 4 天每天都有 rank=1，谁排第一由数据库决定 |
| `assets/cloud.js:108` | `var latest = String(all[0].topic_date)` | 注释写的是「取库里**最新那一天**」，但 `all[0]` 并不是最新那天 |

**为什么以前没暴露**：Day 17 建表时库里只有一天数据，`all[0]` 天然就是那一天；
库里出现第 2 天快照（10-06）之后就开始坏。

**修法（候选，等 Jimmy 定）**：甲 = `db.js` 排序补一句按 `topic_date` 倒序；
乙 = `cloud.js` 不赖排序，从 `all` 里自己算最大的那个日期。**建议乙**（更稳，且与「能现算就现算」一致）。

### 二、为什么这么做

**① 为什么先「自己预检」再去叫人试？**
叫朋友来试之前，先用一个**全新的浏览器档案**（等于「一台没配过任何东西的电脑」）打开线上地址 ——
如果线上本身是坏的，朋友反馈回来的「卡点」全都会是同一句话，真正值得看的可用性问题会被淹没。
**结果这一遍预检恰好撞上了今天最大的坑。**

**② 那个 bug 是怎么被发现的（完整因果链）**

预检看到：版面全正常，但「今日热点」显示 **「这次没读到 · 云端组件没加载成功」**，
「内容库」三列同理。顺着往下查：

| 环节 | 实测结果 |
| --- | --- |
| 线上页面本身 | **HTTP 200** → 网站是活的 |
| `curl` 直连 `cdn.jsdelivr.net`（SDK 来源） | **HTTP 000**，0.386 秒失败 |
| `curl` 走本机 127.0.0.1:1710 代理 | 也是 **000**（2 秒失败） |
| `curl` `registry.npmjs.org`（对照组） | **200** → 不是「整个外网断了」 |
| DNS 解析 `cdn.jsdelivr.net` | **正常** → 解析没问题，是 **TCP 连不上**（被墙的典型特征） |
| 浏览器里那条 SDK 请求 | `duration 713ms`、**`transferSize 0`** → 一个字节都没传过来 |
| `typeof window.WorkBuddyCloud` | **`undefined`** → SDK 确实没挂上 |

**结论**：只要用户的网络**直连 jsdelivr 不通**（国内很常见），
「今日热点」＋「内容库三列」（Day 17 / Day 18 起都读云端）**就整块显示「没读到」**。
云端数据库本身是好的 —— **坏的是「把 SDK 送进浏览器」这一段**。

**③ 为什么这个坑特别阴**
Day 26 截图时热搜还正常显示（说明那天 CDN 通），所以这是**间歇性**故障：
开发机上看着是好的，用户那边可能是坏的 —— 正是今天题眼说的那种「我从没想过的地方」。
而且页面**不报错**，只是那一块空着，不专门看根本发现不了。

**④ 为什么修法是「本地化」而不是「换个 CDN」**
- 换个能用的 CDN，仍然是「在线资源」，依旧违反 `AGENTS.md` 第 4 条第 2 项
  （原文那句 CDN 其实**早就违规了**，是 Day 17 在「不引 CDN」和「零构建」之间做的妥协）；
- 本地化**一次满足三条**：不引任何在线资源 ✓ / 仍然零构建（就是个本地 `.js`，双击 `file://` 也能加载）✓ /
  不受 jsdelivr 被墙影响 ✓。
- 版本上刻意选了 **同一个版本**（`dist-tag dev` = `0.1.3-dev.c090db7.202610050023`，
  与原来引的 `@dev` 一致）→ 除了「从哪加载」，行为**一个字不变**。

**⑤ 这一条值得单独记住**
**当年那个「刻意写进白名单的例外」，正是今天这个 bug 的来源。**
检查工具当时为了「不误报」而放行它，是对的；但放行不等于它没问题 ——
Day 27 把白名单清空，等于把这个例外连同它的隐患一起收掉了。

### 五、试用引出的一个**新问题**（不是反馈，是顺着反馈查出来的）

**产出**：决策材料 `docs/day27-multiuser-and-privacy-advice.md`（同日新建）——

#### 6.3　今日热点：先摘掉，同时把「每天更新」的机器搭起来

**先摘掉**：`config.hot.visible: false` —— 首页整块不画，**也不去云端读它**。

**但摘掉不等于放弃它** —— 同一天把自动更新搭好了，分三件：

1. **新建 `tools/hot-topics/update-daily.mjs`**：抓百度实时热搜 → 生成一条可直接执行的 SQL。
   为什么只生成 SQL 不直接写库：网页那侧只有读权限（路线A 收的），写库必须走管理员通道。
   ⚠️ 抓的是**公开页面里的 `<!--s-data:...-->` 数据块**，不是官方 API（百度没开放热搜接口）——
   所以每一步都带断言，字段一变就**报错退出、绝不写半份数据**。
2. **当天就把数据补到最新**：`topic_date = 2026-10-13`，30 条，含热度值（`790.48w` 这种格式）。
   库里现在是 3 份快照（10-03 / 10-06 / 10-13）。
3. **建了一条每天 8:00 的定时任务**（名字「每日更新『今日热点』快照」）：
   跑脚本 → 执行 SQL → 回读验证 → 汇报。抓不到就如实说「今天没抓到」，**不编、不用旧数据顶**。
   → 也就是说他要的「一天一更、最好更新到当天」**已经能做到当天**，不需要「滞后一天」那个退路。
   等明早跑通一轮验证过，把 `hot.visible` 改回 `true` 就恢复显示。

⚠️ **踩坑记录（当天实测）**：页面给的 `hotScore` 是**字符串**（`"7903997"`），
第一版脚本按数字判断 → 30 条热度**全丢成空**，而且**不报错**、安安静静写进库，
页面上只是「热度那一格不见了」。修法：一律 `Number()` 转一遍，转不出来就当没有（不猜、不补 0）；
另加一道防线 —— 超过一半没热度就直接判定「页面结构改了」，整次作废。

⚠️ **踩坑记录 2（当天第二个坑，这个比上面那个更值钱）**：
那条 SQL 我第一版写成「数据修改型 CTE」—— 想用**一条**语句把「删当天 + 插新的」合成一步，
注释还理直气壮写着「天然幂等」。**它不幂等。**

当天第一次跑成功；**第二次跑必失败**，报
`DATABASE_23505 duplicate key value violates unique constraint "hot_topics_pkey"`。
原因：PG 里 `WITH` 的数据修改子语句和主查询**共用同一个快照、并发执行**，互相看不见对方的效果 ——
所以 INSERT 做唯一索引检查时，那个旧行**还没被标记成删除**，于是撞主键。
（当晚用一张临时表两分钟就把它验死了，没靠猜 —— 建表 → 塞一行 → 跑那条 CTE → 报同一个错 → 删表。）

**为什么这个坑更值钱**：它**首次跑一定成功，只有「重复跑」才炸。**
而自动化里最常带的一句就是「失败就重试一次」—— 那正好等于「第一次成功、重试必失败」，
看起来像网络抖了一下，查起来极费劲。
→ 修法：脚本改成**输出两条语句**（`.tmp/hot-01-delete.sql` 先跑 ＋ `.tmp/hot-02-insert.sql` 后跑），
执行侧依次跑两条；那条每天 8:00 的定时任务说明也同步改了。

#### 6.5　★ 今天第二个值得记的坑：把 config 当 data 用，而 catch 把它伪装成「读不到」

**现象**：改完发布，线上内容库显示 **「内容没读出来」**（读失败的样子）。
**但**直接调接口是好的 —— `ok:true`、16 行、数据好端端躺着。

**定位过程**（值得留下的手法）：异常被 `loadLibrary` 末尾那个 `.catch` 吞了，控制台什么都没有。
→ 用 CDP 打开 `Debugger.setPauseOnExceptions('all')`，直接抓到那一下：

```
TypeError: Cannot read properties of undefined (reading 'replace')
  at updateLibraryToolbarStatus (assets/app.js:1237)
  at renderLibraryToolbar        (assets/app.js:1224)
  at renderLibraryReady          (assets/app.js:1057)
```

**根因**：我在新工具条里写了 `var T = C.libraryTools`（**配置**：开关和上限），
却拿它去取 `T.count`（**文案**：状态行那句话）—— 文案在 `D.libraryTools` 里。
取错的后果很典型：开关全是 true（看着一切正常），但所有文字都是 `undefined`，
而 `h()` 会**悄悄跳过 undefined** → 画出一排**没有字的按钮**，不报错也不明显。

**两个修复，第二个比第一个更值钱**：

1. 分清 `SW = C.libraryTools`（开关）和 `T = D.libraryTools`（文案）。
2. **把渲染从那个 `.catch` 前面挪出来，并且渲染这一环后面不再挂 catch。**
   原来渲染也在 `then` 里、后面紧跟着 `catch` → **渲染阶段抛的任何异常都会被吞掉**、
   统一显示成「内容没读出来」。结果是：数据明明读回来了，页面却指着「网络/数据」说问题在那儿 —
   **报错指向的方向完全是错的，比不报错还难查。**
   → 改完：读失败才说读失败；渲染真出错就照常抛到控制台，**不伪装成数据问题**。

> ★ 这条值得单独记住：**一个 catch 抓得太宽，会把「别处的错」伪装成「它以为的那种错」。**
> 兜底要兜得住，但不能顺手把别的错误也改个名字。

### 八、第三轮：修掉两处「编出来的数字」（2026-10-13 深夜）

**8.1　病是什么**

是**同一类病**：页面上印着一个数字，但它不是从任何真实数据算出来的。

**8.2　怎么改（不是改成正确的新数字，而是改成「算」）**

⚠️ 关键取舍：**没有**把 `12` 改成 `16`。那样只是把一个旧谎话换成一个新的 ——
明天加两条内容，它就又不对了。做法是让它**永远现算**，跟 Day 10 的 `from:'actions'` 一个套路：

- `data.js`：`stats[0]` 改成 `{ label: '内容库收录', from: 'library' }`；
  `meta.updated` 那一个写死的字符串换成**模板**（`updatedTpl / updatedPending / updatedEmpty / updatedUnknown`）；
  新增 `libraryStat` 文案块。
- `app.js`：新增 `libraryStat()` —— 直接数 `libCache`（就是内容库列表用的**同一份数据**），
  所以卡片说 16 条，列表里就一定能数出 16 条；新增 `metaUpdatedText()`，
  那句「内容更新于 X」取内容库最新一条的日期（`rules.js` 的 `daysAgo()`，
  跟每条下面那个「N 天前」**同一个来源**）。
- `app.js`：新增 `ensureLibraryCount()` —— 首页**补读一次**内容库。
  为什么必须补读：内容库的数据原来**只有**进「内容库」页才读，首页从来不读，
  那这两处除了写死没有别的办法。只读一次（`libLoaded` 旗子），读到过就不再请求。
- 三种状态都要说人话：读取中 → 「正在读取内容更新时间…」；读不到 → 明说读不到；
  库里空 → 「内容库还没有收录内容」。**一律不拿旧值顶上。**

**8.3　踩到的两个小坑（都记下来）**

1. **`libCache` 不能当「读没读过」的判据** —— 它的初值是 `[]`，
   而空数组在 JS 里是**真值**，拿它判断会永远为真，首页一次都不会去读。改用显式的 `libLoaded` 旗子。
2. **第一次我把 `metaUpdatedText()` 的判断顺序写反了** —— 先看 `libNewest`、后看 `libState`。
   结果「读失败」时统计卡已经老实说了「暂时读不到」，旁边那句**还挂着上次读到的「今天」**；
   同一份数据、同一屏里两种说法。把顺序掉过来（先说**当下这次读的结果**，再提上次读到的值）就对了。

**8.4　怎么证明能用**

- **本地**（自己起的静态服务 + 无头 Edge）：`内容更新于 今天`；
  `内容库收录 16 条 · 认知 · 自律 7 · 名人访谈 5 · 政策 · 经济 · 风口 4`。

**10.4　热点块的内容过滤**

**为什么要加**（上一轮我提出来的）：这一块拉的是**百度实时热搜原榜**，

**做法（三处分工，照本项目的老规矩）**：

| 放在哪 | 放什么 | 为什么放这儿 |
| --- | --- | --- |
| `config.js` | **词表** `hot.blockWords`（分五组：时政机构 / 违纪案件 / 军事冲突 / 伤亡讣闻 / 恶性案件） | 常量只在一个地方；要加要删只动这一处 |
| `rules.js` | 纯函数 `filterHotRows(rows, words)` | 「算」的活儿归纯函数，可以单独验、不依赖页面和网络 |
| `cloud.js` | 在 `fetchHotTopics` 里**先过滤、再取前 N 条** | ⚠️ 顺序是关键 |

**⚠️ 三条设计上的取舍，都写进代码注释了**：

1. **只匹配标题，不匹配摘要。**
   摘要是百度给的背景说明，民生政策类条目常在摘要里提到「国务院印发…」。
   一起匹配会把**对大学生真正有用的政策内容**也误伤掉 ——
   实测当天那条「未来五年看病就医会有哪些新变化」就是标题干净、摘要里带「国务院」，
   只匹配标题它就留下来了。
2. **在 cloud.js 滤，不在 app.js 滤。**
   页面是按 `limit` 先取前 N 条再画的。先取 8 条、画的时候滤掉 3 条，
   榜上就只剩 5 条 —— 看着像缺了一块，展示数也跟 `limit` 对不上。
   **先滤、再取前 N 条**，展示数才是满的。
3. **`total` 的含义变窄了，所以必须同时把 `blocked` 交出来。**
   加了过滤之后，「共 N 条」说的已经不是「库里这一天有 30 条」，
   而是「这一天有 25 条**是本站会展示的**」。
   不说「另有 5 条未展示」，拿它跟百度原榜对照的人会以为**数据缺了一块**。
   → 25 ＋ 5 ＝ 30，这样两个数才闭合。**同一个数字只说一半，就是新的不实。**
   （契约变更已写进 `docs/api-contract.md` —— 这是本次唯一一处「老字段含义变了」。）

**另外处理了两个边界**：
- **滤到一条不剩**时**不画空榜单** —— 空列表看着就是「页面坏了」，
  给一句实话（「这一天榜单里的内容都跟本站主题无关」）。
- **加载顺序的坑**：`rules.js` 在 `cloud.js` **后面**才加载，所以
  `var R = window.GROWTH_RULES` **不能**写在文件开头，只能放在异步回调里取；
  取不到就**不过滤**（宁可多留一条，也不要因为一个加载问题把整块清空）。

**词表怎么定的**：先按「五类明显不合适的」写，然后用**当天的真数据**跑一遍看结果，
再补上几个漏掉的（第一版漏了「溺亡」「遇害」「失联」「轻生」，实测发现的）。

**10.6　★ 关于推送：不是「两条路都不通」，是「**一条路本来就死、另一条偶发抖动**」**

这一轮先按老办法试了两条路，两条都报错：

| 试法 | 报错 |
| --- | --- |
| 直连（= 走环境变量里的代理） | `CONNECT tunnel failed, response 502` |
| 本机中转口 `127.0.0.1:1710` | `Failed to connect to github.com:443 over proxy 127.0.0.1 after 2049 ms` |
| `git ls-remote` | 同上 502 |

以前到这一步就「转给 Jimmy」了。这次多做了**一步对照测量**，结果把病因分开了：

| 测什么 | 结果 |
| --- | --- |
| `curl -x http://127.0.0.1:57097 https://github.com/`（**环境变量里的代理**） | **200 / 200 / 200**（连测三次全通，1.7–3.4 秒） |
| `curl -x http://127.0.0.1:1710 https://github.com/`（**我一直当备选的那个中转口**） | **000 / 000 / 000**（每次都 2.0 秒超时） |
| `git ls-remote origin main`（什么都不加） | 之后连测 **3 / 3 成功** |

**两个结论：**

1. **`127.0.0.1:1710` 这个口已经彻底死了** —— 它一直在记录里当「备选路线」，
   但从某一刻起就没人监听了。⚠️ **以后再试它纯属浪费一次尝试**，
   而且它给出一条**误导性**的报错（「Could not connect to server」听着像网络断了，
   其实是那个端口根本没服务）。→ **从今天起，1710 这条路线从记录里删掉。**
2. **能用的那条路是环境自带的代理** `HTTPS_PROXY=http://127.0.0.1:57097`。
   `curl` 3/3 通、`git ls-remote` 3/3 通、**推送也是走它成的**。
   git 本来就会自己读这个环境变量 —— 所以**主路径就是「什么都不加、直接 `git push`」**，
   不需要再手工指定任何代理。

**修正上一轮的结论**：上次写「两条路都不通，是出口代理到 GitHub 的通道问题」——
**那半句对、这半句错**。真相是：**一条路本来就死（1710），另一条偶发抖动（57097）**。
所以：

- `AGENTS.md` 第 7 条「**推送由助手直接推**」**站得住**，不用改回去；
  但补一句操作纪律：**报错后隔一会儿重试一次**（今天就是重试一次成的），
  **不要一失败就转给 Jimmy** —— 转了也是白转，他那台机器走的是同一个出口。
- 判断口诀：见到 `CONNECT tunnel failed, response 502`，先量
  `curl -x http://127.0.0.1:57097 -o /dev/null -w "%{http_code}" https://github.com/` ——
  **通了就是抖动，重试即可；`000` 才是真断，那时候再叫他。**

| 环节 | 实测结果 |
| --- | --- |

### 五、定时任务里抓到一个真 bug：CTE「先删再插」不幂等

每天的热搜快照脚本原来输出**一条**「数据修改型 CTE」（先按日期删、再插 30 条），注释写「同一天重跑天然幂等」——
**实测不成立**：当天 22:03 已成功写过一次，22:09 再跑同一条 → `DATABASE_23505 duplicate key`。

原因：PG 里 `WITH` 的数据修改子语句与主查询**共用同一快照**，INSERT 做唯一索引检查时旧行还没被标记删除。
→ **当天第一次能成，第二次必失败**（delete 那半句从来没真正生效）。

修法：脚本改成输出**两个文件** —— `.tmp/hot-01-delete.sql`（先跑）＋ `.tmp/hot-02-insert.sql`（后跑），
执行侧**分两次工具调用**。没采用 `ON CONFLICT`：它只覆盖同一批 id，某天条数变少（比如只抓到 25 条）时，
旧的 `-26`~`-30` 会留在库里变成脏尾巴。

### 三、四条关键设计（每一条都是被真实坑逼出来的）

1. **三态，不是两态：通过 / 失败 / 未检查。**
   「未检查」= 这一项**没能跑成**（断网、环境限制），它**不算通过**。
   汇总里单独计数 —— 绝不用「没查」冒充「没问题」。这条是整个 Skill 的地基。

2. **匹配前必须剥注释。**
   项目里的注释大量提到 `innerHTML` / `localStorage` / `toISOString`（都在讲「别用它」），
   照着原文匹配**必然误报**。所以 `.js` 先剥掉行注释和块注释、`.html` 先剥掉 HTML 注释，
   **且保留换行**（行号才不错位），再去匹配真代码。

3. **B2 有一个「白名单」，是刻意的。**
   `index.html` 里那个云端 SDK 的 CDN（Day 17 加的）是**有意的例外**：
   纯静态 + 零构建，引 npm 包就得多一道构建步骤。
   所以检查项放行它、但对**任何第二个外部资源报警**。
   → **检查项要跟项目真实约定对齐，不能照文档一刀切**：照文档写「禁止一切在线资源」，
   会对一个正常项目报红 —— 那叫误报，和漏报一样会让人不再信任这份报告。

4. **零子进程、零依赖。**
   受限环境里 `spawn` 会被挡（`EBUSY`），脚本就会**假装检查不了**。
   所以文件清单做了两条通道：
   `git ls-files`（权威）用不了时，自动退回「目录遍历 + 自己解析 `.gitignore`」；

## Day 24｜2026-10-10　修掉一个真 Bug：把「来源名」当成了「人名」

> 今天的板块：① 复现 Bug　② 定位　③ 修复　④ 验证留证。
> 完成标准：四步证据齐全；修复已提交。

### 一、复现：这个 Bug 长什么样

内容库 → **名人访谈**那一栏，有一条（`u-2026-10-07-q77`，标题「我验过了」）
显示成：

```

```

而它下面那条正常的同栏目内容是：

```
长访谈 · 约 22 分钟 | 雷军 · 小米创始人
```

**差在「人物」那一格**：正常是「**雷军**」（人名），错的那条是「**雷军访谈**」——
**把节目名当成人名**印在了页面上。

⚠️ 这一条**不抛异常、控制台干净**，所以它不是「红字报错」，而是**页面上印出来的错误文本**
本身就是证据。这一点很关键：**「没有报错」不等于「没有问题」**。

### 二、定位：怎么排除掉其他原因、锁定真正原因

一开始有三个「看着像」的嫌疑，逐个用证据排掉：

| 嫌疑 | 排除方式 | 结论 |
|---|---|---|
| ① 徽标印成「长访谈」（少了一段时长） | 查这行数据 `dur` 确实是空 | **不是 Bug** —— `mediaBadge` 的设计就是「没时长只写形态」，它是**对的** |
| ② 数据库里 `src.name` / `src.note` 坏了 | 直接查 `sources` 表 | **不是** —— 两个值都合法（`雷军访谈` / `小米创始人`） |
| ③ 整个访谈栏渲染都坏了 | 看另外 3 条 | **不是** —— 那 3 条完全正常，说明不是渲染代码整体出问题 |

**唯一剩下的变量**：这条数据的 `detail` 是 `null`（缺 `person`），而其它 3 条 `detail.person` 有值。
把「输入 → 输出」逐条打出来对照，根因就落在**一行代码**上（`app.js:1100`，改前）：

```js
it.person = d.person || src.name || '';   // ← 缺 person 时，拿「来源名」当人名兜底
```

- `src.name` 是**来源 / 节目名**（「雷军访谈」），它的含义是「这条内容**出自哪儿**」；
- `d.person` 才是**人物姓名**（「雷军」）。

**这两个根本不是一个东西**，旧代码把它们当成了一个 —— 这是**语义错位**，不是空值保护。

**为什么一直没被发现**：示例内容每条的 `detail` 里都规规矩矩填了 `person`，
那一路「兜底」**从来没被走到过**；直到一条 `detail` 为空的新内容（表单加的那条）进来才露出来。

> ⭐ 这一条就是今天要掌握的能力：**不是「看着像就改」，而是把「其他可能」一个个用证据排掉**，
> 最后剩下的那个就是真因。中途我还误判过「长访谈」是 Bug，是**查了数据**才知道那是对的行为。

### 三、修复

`assets/app.js` 的 `entryFromRow()` 里，**一行**：

**缺 `person` 就不显示人名**，不用别的东西冒充。

所以**不会留空壳**——那一格整段不画，这是项目一贯的「没有就不画」的规矩。

`src.note` 存的本来就是「人物身份」（小米创始人），跟人名不是同一个概念，

## Day 22｜2026-10-08　PATCH / DELETE 上线：增删改查四类操作闭环

> 今天的板块：① PATCH 实现　② DELETE 实现　③ 四类操作闭环验证。
> 完成标准：PATCH 修改一条数据生效；DELETE 删除后 GET 不再返回；四类操作闭环。
> **今天不做**：批量操作、用户系统。

**做了什么**

**① 接口层加两个写函数**（`assets/db.js`）

| 函数 | 干什么 | 关键判据 |
| --- | --- | --- |
| `updateContent(row)` | 按 `id` 改一条 | **返回里必须有那一行**才算改成 |
| `deleteContent(id)` | 按 `id` 删一条 | 用 `.select()` 把被删的那行捞回来，区分「删了 0 行」和「删了 1 行」 |

两个函数都**不带 id 就当场挡回** —— 少这一步，一条不带条件的 `UPDATE` / `DELETE`
会改到 / 删掉整张表。这是这一层最不能犯的错。

**② 接口层加两个契约函数**（`assets/cloud.js`）

- `patchEntry(input)` / `deleteEntry(id)`，外加 `MISSING_ID` / `PATCH_FAILED` / `DELETE_FAILED`
  三个错误码和 `entryPatchFail` / `entryDeleteFail` 两个翻译器。
- **`patchEntry` 刻意不做「先查重」**（和 `postEntry` 明显不同）：
  POST 是「凭空多一条」，重名必须提前拦；改的却是**我自己这一条** ——
  万一只改摘要、标题一字没动，再查一次重就会把「我自己」查出来，
  把一次正常修改误判成重复。重名兜底交给数据库的唯一约束。
- **`deleteEntry` 删完必须回查**（今天的地基，见下）。

**③ 界面：每一条内容加「改 / 删」入口**（`assets/app.js`）

- `entryFromRow()` 补上 `id` / `sourceId` / `summary` —— 不加 `id` 就无从定位要改 / 删哪条。
- `renderEntry()` 给每条画两个按钮；只给**真的从云端读回来、有 id 的**条目画
  （本地写死的那些没有 id，画了必然失败，不如不画）。
- 新增 `openEditForm()` / `askDeleteEntry()` / `cancelEditEntry()`。
- **表单复用**：编辑和新增要填的东西完全一样，所以**不新做表单**，
  让「新增一条」那块进入「编辑模式」（旧值填回、按钮变「保存修改」、多一个「取消」）。
  另做一份必然导致「新增时校验、编辑时忘了校验」这种不一致。

**④ 数据库开两扇门**（`db/schema.sql` 追加 Day 22 段，并已在云端执行）

`contents` 表上 `anon` 原来只有 `SELECT` + `INSERT`，今天补上 `UPDATE` + `DELETE`：

```sql
GRANT UPDATE ON TABLE public.contents TO anon;
GRANT DELETE ON TABLE public.contents TO anon;

CREATE POLICY contents_update_guard ON contents FOR UPDATE TO anon, authenticated
  USING (kind = 'entry')
  WITH CHECK (kind = 'entry' AND source_id IS NOT NULL
    AND char_length(btrim(title)) BETWEEN 1 AND 60
    AND char_length(COALESCE(summary,'')) <= 200
    AND media IN ('video','article','podcast','talk')
    AND created_via = current_user);

CREATE POLICY contents_delete_guard ON contents FOR DELETE TO anon, authenticated
  USING (kind = 'entry');
```

**为什么这么做（今天最硬的一条设计）**

**⚠️ `UPDATE` 策略要 `USING` + `WITH CHECK` 两半，`DELETE` 只要 `USING`。**

| 两半 | 管什么 | 只写一半会怎样 |
| --- | --- | --- |
| `USING` | **哪几行**你有权动（进门前筛） | 只给 `USING` → 能把任意一行改成任意样子（包括把 `kind` 改成 `read`） |
| `WITH CHECK` | 改完**必须仍然长这样**（出门前再筛） | 只给 `WITH CHECK` → 等于整张表每一行都能改（门槛没了） |

`DELETE` 没有「改完的样子」可验，所以只有 `USING`。
`WITH CHECK` 里锁死 `kind = 'entry'` 和 `created_via = current_user` ——
这是这一行的「身份」，改了就等于「换一种数据」或「冒充别人写的」。

**⚠️ 删除为什么比新增更容易出事**

- 新增写错，最坏是库里**多一条**，删掉就回去了 —— **可逆**。
- 改是**覆盖原值**（旧标题 / 旧摘要没有任何地方还留着）；删是**不可逆**的。
- 更阴的一点：PostgREST 删一条**本来就不存在的**记录，返回的是
  「成功、删了 0 行」，**不报错**。所以「没报错」根本不能当成功判据 ——
  那就成了「删错了也以为删对了」的入口。

**确认加在哪？两处：**

1. **界面上**：内容库每条的「删」按钮走 `confirmDanger()`，弹出确认框，说清三件事 ——
   删的是云端哪一份、刷新后什么变化、**能不能撤销**。
   （AGENTS 第 4 条第 11 项：每加一个删除入口都要先问；这是本项目第 2 个删除入口。）
2. **数据库那一侧**：`contents_delete_guard` 的 `USING (kind='entry')` ——
   只能删「内容库」这一类，删不了「今日一篇」（防顺手删掉首页内容）。

**怎么证明能用**

**① 动手之前先量**：写了个权限探针，用**不存在的 id** 去 update / delete。
用不存在的 id 的好处：即使权限开着也只「改 0 行」，**真实数据一行不碰**，可以随便跑。

## Day 18（续）｜2026-10-04　内容库能自己加一条了：第一个 POST 接口

> ⚠️ **编号说明**：昨天（10-03）那两条提交用的也是「Day 18」。
> 今天按 Jimmy 的清单继续用 Day 18，这里加「（续）」区分。

**今日学习点**：一个「提交」按钮，要防的是哪几种「不对劲的提交」？

**答案**：**两种 —— 一种防填错，一种防重复提交；而且两种都要防两层。**

| 防的东西 | 页面这层（为了快） | 数据库这层（为了真） |
| --- | --- | --- |
| 填错（缺必填 / 超长 / 形态不认识） | 当场回中文提示，**根本不发请求** | INSERT 策略的 `WITH CHECK` 再判一遍 |
| 重复提交（同一来源下标题已有） | 提交**前**先查一次 → `DUPLICATE` | `UNIQUE` 约束 → `23505` |

**「两层」是今天最值钱的一句**：页面那层是**体验**，数据库那层才是**安全**。
只有第一层的接口等于没防护 —— 页面代码能被绕过，表结构不会。

（完整答案、实测表、踩的坑 → `docs/day18-post-endpoint.md`）

---

**做了什么**

- **先定契约**：新建 `docs/api-contract.md`。把入参、出参、9 个错误码、每一句中文提示
  **先写死**，再照着它写代码。清单里「形状与 api-contract.md 一致」指的就是这个文件。
- **接口**：`assets/cloud.js` 加 `postEntry()`（校验 → 查重 → 写入 → 读回 → 统一形状）；
  另加 `validateEntry()`（纯函数）和 `fetchSources()`（表单下拉要用库里的真 id）。
- **表单**：「内容库」视图加了一块「新增一条」。`app.js` 画 + 收提交，
  `style.css` 给样式（**虚线边框**跟榜单区分开：上面是「看的」，这里是「动的」），
  `index.html` 加挂载点，文案进 `data.js`，数字进 `config.js`。
- **开权限**（`db/schema.sql` 的 Day 18 段，同步落到云端）：
  - `GRANT INSERT ON contents TO anon` —— **只给新增**，UPDATE / DELETE 一个字没给
  - `CREATE POLICY contents_insert_guard … WITH CHECK (…)` —— 字段校验 + 留痕字段不许伪造
  - `UNIQUE (source_id, title)` —— 防重复提交的最终防线
- **上线**：`https://source-board.app.workbuddy.host/`

**⚠️ 有一件事要单独说：这是全项目第一次「网页能写」。**

Day 16 / 17 定的边界是「网页只能读、不许写」。今天开了一个**只允许新增**的口子。
代价是**任何打开这个网页的人都能写一条**（这个项目不做登录，页面用的是匿名身份）。

**这不是漏想** —— 是摊开算过、然后选择接受的：

- **得到**：以后你自己在页面上就能加内容，不用再走「改 data.js → 找 AI → 提交 → 推送 → 发布」那一圈；
- **换来**：管不住「谁来写」，就**把门开小** —— 只给 INSERT（不能改不能删）、
  字段长度卡死、`kind` 和 `media` 限定取值。

**余力加练：加一条服务端日志**

这个项目**没有服务器**（纯静态页面 + 托管数据库），所以能「在服务端记一笔」的地方
只有**数据库自己**。做法：给 `contents` 加一列 `created_via`，
默认值填 `current_user` —— 网页写的记成 `anon`，维护者通道写的记成管理员角色名。

⭐ **重点不是「加了这一列」，而是它改不了**：前端要是自己塞一个 `created_via:"admin"`，
INSERT 策略里那条 `created_via = current_user` 会当场把它顶回去（`42501`）。
**一份能被写的人自己改的记录，等于没有记录。**

**验证怎么做的**（都真跑过，不是「应该没问题」）

| 试的事 | 结果 |
| --- | --- |
| 空标题点提交 | 「标题不能为空」+ `MISSING_TITLE`（**这一步没发网络请求**） |
| 不选来源点提交 | 「请选择一个来源」+ `MISSING_SOURCE` |
| 正常提交（线上真地址） | `{ok:true, id:"u-2026-10-04-2kw", …}`，形状与契约完全一致 |
| **同一条再交一次** | `{ok:false, code:"DUPLICATE", message:"这条内容已经在库里了…"}` |
| 回查数据库 | **真的多了一行** · 总行数 20 → 21 |
| 伪造 `created_via:"admin"` | 被数据库拒：`42501 new row violates row-level security policy` |
| 页面 JS 报错 | **0 条** |

**踩的两个点**

1. **空数组 ≠ 成功。** RLS 把写入挡住时，PostgREST **不给 error**，只给一个 `data: []`。
   当成成功处理，就会出现「页面说存好了、库里什么都没有」——**比报一串错还糟**，
   因为没人会去查它。所以 `insertEntry()` 里专门判了这一条，宁可报 `WRITE_FAILED`。
2. **「先查后写」拦不住并发。** 提交前那次查询只是为了让**提示准**
   （一句中文，而不是一串英文错误码）。两个人同时提交时它拦不住 ——
   真正的防线是唯一约束。**任何「先查再写」的逻辑都要问一句「两个人同时做会怎样」。**

## Day 18｜2026-10-03　整页铺上了 Jimmy 自己拍的视频

> ⚠️ **这条是「先做完、等他看了才提交」的**。Jimmy 原话：
> 「该给我看看吧，如果更改完善后，某些地方冲突太大，我再复原」。
> 所以顺序是：做出来 → 截图给他看 → 他说「行」→ 才写这条日志、才提交。

**今日学习点**：一段看着没问题的视频，为什么浏览器根本不播？

**答案**：**编码格式不对，而且是从源头就不对。**

Jimmy 给的是手机拍的 `.mp4`。肉眼看着是个正常视频文件，
但浏览器里**完全不播**。查法是三行 JS：

- `canPlayType('video/mp4; codecs="hvc1"')` → 返回**空字符串**（不是 "maybe"，是空）
- 真去加载 → 报 `MEDIA_ELEMENT_ERROR: Format error`（错误码 4）

**根因**：原始文件是 **HEVC / H.265** 编码。
Chromium 系浏览器（Edge / Chrome）**出厂不带 H.265 解码器** ——
H.265 有专利授权费，浏览器厂商默认不装。
**「文件能打开」和「浏览器能播」是两件事**，这是今天最值钱的一句。

---

**做了什么**

- **转码**：用 `imageio-ffmpeg` 自带的 ffmpeg，把 H.265 转成 **H.264**：

  ```
  ffmpeg -y -i "原视频.mp4" -c:v libx264 -preset slower -crf 30 -pix_fmt yuv420p \
         -an -vf "setpts=1.5*PTS,scale=1104:-2" -r 24 -movflags +faststart \
         "assets/hero-sea.mp4"
  ```

  - `-an` 去音轨（背景视频不需要，还能瘦身）
  - `setpts=1.5*PTS` **慢放 1.5 倍** —— 原片动得偏急，慢下来才像「氛围」不像「GIF」
  - `+faststart` 索引挪到文件头，边下边播
  - CRF 试了三轮：23 → 1.76MB 偏大；26 + 放大到 1280 → 1.81MB（**放大反而更大**）；
    **30 保持原尺寸 → 1.01MB**，画质够用

- **新增 `assets/hero-video.css`** —— 视频背景的**全部**样式，单独一个文件。
  想关掉只要删 `index.html` 里一行 `<link>`，不用在 `style.css` 里到处摘代码。

- **`index.html` +28 行** —— 一个 `<link>` + 一个 `.bg-video` 块（`<video>` + 压暗层）。

- **新增 `assets/hero-sea.mp4`**（转码后，1.01MB）、**`assets/hero-sea-poster.jpg`**（89KB，网慢时先显示）。

**没动的**：`style.css` / `app.js` / `config.js` / `data.js` / `rules.js` / `store.js`
**一行都没改**。视频层是纯装饰、不在 JS 必经路径上，不挂 `onerror`。

**为什么这么做**

- **三层结构**：`.bg-video`（`position: fixed`，铺满）→ `.veil`（压暗层）→ `.wrap`（原内容）。

**⚠️ 今天踩的四个坑（都只有真跑起来才看得见）**

1. **`backdrop-filter` 做的「磨砂托底」，边界藏不住。**
   想给顶栏 / 导航加托底，做成「圆角矩形 + `blur(10px)`」——
   结果边界清清楚楚，顶上像贴了张**浅蓝膏药**。
   根因：`backdrop-filter` 只模糊元素矩形**范围内**的背景，矩形外不模糊 → 直边必然可见。
2. **改用纯渐变后，半径写太小又出硬边。**
   `radial-gradient(130% 150% ...)` —— 元素只有几十像素高，
   渐变**还没走完就被元素边界裁掉**，出现一块带硬边的暗色矩形，比坑 1 还明显。
   **✅ 最终解法：把视频自己上下淡出（`mask-image`）。**
   `mask` 本来就是「渐隐」，压根不存在边界这回事。
   > 教训：想让某块「边缘淡出」，用 `mask`，不要「给它垫一个带渐变的兄弟元素」。
3. **类名凭印象瞎写，写错的完全没生效。**
   我写了 `.demo-cell` 和 `.entry-item` —— **两个都不存在**（真实是 `.demo-card` / `.entry`）。
   现象是「内容库那四格压在视频上像四块黑板」。顺带发现 `.entry` 是**带下划线的列表行**，
   不是色块，**不能**给它加背景。
4. **bash heredoc 写出来的脚本，反斜杠被吃掉（最阴的一个）。**
   在 `cat > x.mjs <<'SCRIPT'` 里写 `'C:\\Users\\...'`，JS 解析时 `\U` 不是合法转义被丢弃
   → 路径变成正斜杠 → 跟 `path.join` 拼出的反斜杠比 `startsWith` 得 false
   → **静态服务每个请求都 404** → 浏览器打开的是 **Edge 错误页**。
   **症状极阴**：脚本不报错、服务照常起、浏览器照常开，只有「页面内容不对」一个线索。
   我因此**截了一堆「看着像页面、其实是错误页」的图**，还对着它们分析「为什么滚不动」
   （错误页只有 360px 高，当然滚不动）。
   > 教训：**脚本一律用编辑器「写文件」写，不要用 bash heredoc。**
   > 另外静态服务要自测：先 `fetch` 一下 `index.html` 看是不是 200，再开浏览器。

**顺带修的一个小坑**：本地小服务必须支持 **Range（206）**。
`<video>` 一定会发 Range 请求（边下边播、能拖进度条），
只回 200 的话 Chromium 会停在 `readyState 0` 不动 ——
现象是「页面看着正常、视频完全没加载」。

> （`readyState 4`、进度在走）。说明线上那台服务器/反代自己处理得过来，

**今日学习点**：接口返回的数据里，哪一项和你建的表对不上？怎么发现的？

**答案（今天真撞上的）**：**不是「哪一项对不上」，而是「整张表都不在」。**
`hot_topics` 我建在了应用 A（`wbapp_B7sQ…`）里，而网页发布后挂的是应用 B
（`wbapp_e8u8wx…`）。于是网页去 B 里查 `hot_topics`，B 里根本没这张表。
**发现方式**：在 B 上跑 `list_tables`，返回的只有 auth / storage / internal 几个系统
schema —— 我自己建的表**一张都不在**；再查 `sources` 直接报
`42P01 relation "sources" does not exist`，
而 `sources` 明明在 A 里躺得好好的。**「同一个名字，两个库里各有一半」，就是这么发现的。**

**做了什么**

- **新增 `assets/cloud.js`** —— **全项目唯一允许碰云端的文件**。
  - `waitForSdk(timeoutMs)`：**轮询等 SDK 到位**（最多 6 秒），等到才认「真的没有」。
  - `buildClient()`：只建一次客户端（建两次会多一倍请求）。
  - `fetchHotTopics(limit)`：读 `hot_topics`，取**库里最新那一天**的整份榜单，
    返回 `{ ok, rows, date, total }`；读不到就返回 `{ ok:false, reason }`。
  - `localDate()`：用**本地时间**拼日期（`toISOString()` 给 UTC，晚上 8 点后会算成第二天）。
- **`index.html`**：加云端 SDK（CDN）+ `cloud.js`，加「今日热点」容器；
  **修掉一个线上才看得见的坑**（见下）。
- **`assets/app.js`**：新增 `renderHot()`（先画骨架再去读）、`paintHot()`（三种结局分头画）。
- **`assets/data.js`**：加 `hot` 文案块（标题 / 日期 / 来源 / 三种失败说法 / 重试）。
- **`assets/style.css`**：加「今日热点」区块样式（F15）。
- **新增 `db/sync-hot.mjs`** —— 热搜同步任务：从 **60s.viki.moe** 拉百度实时热搜，
  生成 SQL 写进 `hot_topics`。**它是「造 SQL」，不是「直接写库」**（原因见下）。
- **云数据库**：在**正确的那个应用**里建 `hot_topics` 表（11 列）+ 索引 + RLS 两道门 +
  表注释；灌入 **30 条**当日真实热搜。
- **余力加练**：地址支持 `?hot=N` 控制显示条数（`1 ~ 30`）——
  `rules.js` 新增 `hotLimitFromHash()` 纯函数专管校验；`config.js` 加 `hot.limitMax`。

**为什么这么做**

- **为什么 `cloud.js` 要单独一个文件**：跟 `store.js` 同一条规矩（老项目 Day 6 第 6 条）——
  **把「数据从哪来」关在一个文件里**，页面代码一个字都不用知道数据是来自本地抽屉还是云端。
  以后要换数据源，只改这一个文件。
- **为什么必须有 `waitForSdk` 轮询**：第一版写的是「跑的时候看一眼，没有就返回 `no-sdk`」。
  结果首屏**经常**误报「云端组件没加载成功」，而 SDK 其实好好的 ——
  外部脚本是异步下载的，**我的代码可能比它先跑到**。
  → 记牢：**「现在还没有」和「根本没有」是两件事**。
- **为什么同步脚本只造 SQL、不直接写库**：Day 16 定的边界 —— 网页只能读、不许写。
  实测用网页那把钥匙去 POST 写入，服务端返回
  `HTTP 401 {"code":"DATABASE_42501"}`。**这不是坏了，是边界在生效。**
  所以入库走**维护者通道**（本机跑脚本 + 提权写入），跟线上网页那条通道分开。
- **为什么取「库里最新那一天」而不是死认「今天」**：首页不该在零点过后就空掉；
  万一某天忘了跑同步，显示最近一份当日榜单比显示空白有用得多。
  **同时把日期一起显示出来**，让人能分清这是哪天的。
- **为什么 `endpoint` 必须和网页自己的域名完全一致**：
  服务端按**来源（Origin）精确匹配**。用错了会被一口回绝
  `HTTP 403 {"error":"access_denied","error_description":"the request origin is not allowed for this client"}`。
  **最坑的是浏览器不告诉你这个 403** —— 它统一报 `TypeError: Failed to fetch`，
  看起来像断网；而**不带 Origin 的 curl 却是 200**，于是极容易查错方向。
- **为什么 `?hot=N` 要封顶 30**：库里一天就 30 条；写 99999 只会让页面白等、白画一堆骨架，
  一个手抖就能把首屏撑爆。认不出来（`hot=abc`、`hot=2.5`、`hot=0`）**一律静默回默认** ——
  跟其它「外面来的数据」一样，**不许因为一个手抖就白屏**。

**怎么证明能用**

- **接口**：带 `Origin` 打公网数据面地址 →
  `HTTP 200`，返回真实 JSON（rank 1「自驾回家车主：回程或要弃车打飞的」780.9w 等）。

- **「改一行、刷新后跟着变」**（清单里的完成标准）：
  在控制台执行 `UPDATE hot_topics SET title = title || '【改过一行验证】' WHERE id='baidu-2026-10-03-01'`，
  刷新页面 → 探针读回 `title: "…打飞的【改过一行验证】"` ✅（验证完已**还原**）。
- **`?hot=N`（余力加练）** 线上实测 5 组：

  | 地址 | 实际显示 | 页面标记 |
  |---|---|---|
  | `#/home` | 8 条 | 共 30 条 · 本次显示 8 条 |
  | `#/home?hot=3` | 3 条 | **你指定了 3 条** · 本次显示 3 条 |

⚠️ **今天踩了三个「只有真开浏览器跑线上才看得见」的坑**，都写进代码注释了：

1. **HTML 行尾注释陷阱**：原来写成
   `<script src="assets/x.js"></script>  <!-- 说明 -->`，
   **线上整页 JS 全不执行**（页面只剩空骨架），本地却一切正常。
   原因：浏览器把那段行尾注释的开头当成了脚本内容，把后面的标签结构全吞掉。
   → **注释一律写在脚本标签外面，绝不跟在它后面。**
2. **`endpoint` 用错应用**（就是今日学习点那条）—— 表现为浏览器报 `Failed to fetch`。
3. **`onRouteChange` 会抹掉 `?hot=N`**：它原来拿 `hashOf(id)`（只有 `#/home`）

   表现是「输了 `?hot=3`，页面闪一下又变回 8 条，参数像没生效过」。
   → 改成**只把认不出来的部分纠正掉**：认得出视图就把参数原样留着。

⚠️ **另一个自己给自己挖的坑**：「你指定了 N 条」这个标记第一版只画在**加载中**那版卡片上，
而 `paintHot` 一上来就 `clear(box)` 整块重画 —— 数据一回来标记就没了。
→ 教训：**凡是「用户这次操作的回声」，都必须画在最终那版上，画在中间态等于没画。**

## Day 16｜2026-10-02　云端多了两张表：来源 ＋ 内容

**做了什么**

- **新增 `db/schema.sql`** —— 两张核心表的结构定义：
  - **`sources`（内容的出处）**：准备收录的账号，以及页面上已经用到的书 / 演讲 / 官方文件。
  - **`contents`（内容条目）**：内容库三列（`kind = 'entry'`）＋「今日一篇」（`kind = 'read'`）。
  - **关联字段：`contents.source_id` → `sources.id`** —— 一个来源对应多条内容（**一对多**）。
  - 两张表都开了 **RLS**，策略是**公开可读、客户端不许写**（只建 SELECT 策略，不建增删改策略）。
- **新增 `db/seed.sql`** —— 种子数据：`sources` **18 行**、`contents` **20 行**。
  数据**全部来自 `assets/data.js`**，没有一条是现编的；`url` 一律留空字符串。
  写法用 `ON CONFLICT (id) DO UPDATE` —— **可以反复执行，不会报错、不会插重复**。
- 云数据库：复用发布上线时创建的那个应用，**开通云服务**后建表 → 灌种子 → 跑验证。

**为什么这么做**

- **为什么 `contents.source_id` 设成 `NOT NULL`**：这是 `PRD.md` 硬约束 **C4**
  「页面上出现的每一条内容，都必须能核到原始出处」的**数据库版**。
  **约束写进表结构比写在文档里管用** —— 文档靠自觉，结构靠报错。
- **为什么两张表都选「内容类」、一点不碰用户数据**：
  打卡和收藏是**只有 Jimmy 才有的记录**，`PRD.md` 硬约束 **C3** 明确定着

- **为什么种子脚本必须幂等**：种子经常要重跑（改一行数据、换台电脑重建库）。
