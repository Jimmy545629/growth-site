# 发布前检查 · pre-release-check

## 这个技能解决什么问题

没有它的时候，一次改动的收尾是「提交 → 发布 → 告诉 Jimmy 已上线」。
中间**没有一个固定的动作去回答「这份代码到底能不能发布」** ——
靠的是我（AI）当场记得多少。我记得住的时候是运气，记不住的时候就是把问题带上线。

有了它：**收尾流程里插进一条命令**，12 项检查一次跑完，红就是红、绿就是绿。

> ⭐ 设计上最要紧的一句话：**「没查」不等于「通过」。**
> 所以输出是三态（通过 / 失败 / 未检查），不是两态。
> 断网了、起不了子进程了 —— 检查项会明说「未检查」，
> 而不是安静地跳过去、让人以为一切正常。

## 怎么跑

在项目根目录（`C:\Users\33386\WorkBuddy\growth-site`）里：

```
node skills/pre-release-check/check.mjs
```

参数：

| 参数 | 干什么 |
| --- | --- |
| `--no-online` | 跳过 C 组联网检查（离线时用）。被跳过的项标「未检查」 |
| `--only A1,C1` | 只跑指定项（调试用；对应「卡住降级」的最小版：只查凭据 + 线上可达） |
| `--walk` | 强制走「目录遍历 + .gitignore 解析」的文件清单通道（对比调试用） |
| `--list-files` | 只把文件清单打出来，不跑检查 |
| `--root <目录>` | 指定项目根（本技能的副本在别的目录里调用时用） |

**零依赖**：不用 npm、不用 node_modules、不 spawn 子进程
（`git` 能用就用，用不了自动降级）。所以它不会因为「环境不对」而跑不起来。

**退出码**：有失败项 → `1`；只有通过/未检查 → `0`。
可以直接用在 `&&` 后面，例如「检查过了才允许提交」。

## 检查项：12 项，分三组

### A 组 · 安全红线（碰了就是事故）

| 代号 | 检查什么 | 怎么算通过 |
| --- | --- | --- |
| **A1** | 仓库里有没有真实凭据 | 拿 9 类敏感凭据形状去扫全部文件 → **代码与配置里 0 处命中** |
| **A2** | `.env` 全族有没有被忽略 | `.env` / `.env.local` / `.env.production` / `.env.development` / `.env.test` / `.env.staging` 六个变体**全部**被 `.gitignore` 挡住 |

关于 A1 的两条有意设计：

1. **报告只打印代号和打码片段，绝不回显命中原文。**
   一份检查报告自己把凭据抄一遍，就成了新的泄漏面。
   代号含义写在 `check.mjs` 的注释里，**不进任何文档** —— 同一个理由。
2. **代码里的命中判「失败」，文档里的命中判「通过 + 备注」。**
   文档里出现这些词，通常正是在**讲这件事本身**（比如 Day 23 记录的「特征词清单」）。
   它和「代码里藏了真凭据」是两回事，不该共用一个结论。
   ⚠️ 是**通过 + 备注**，不是「忽略」：位置一条不少地摆在报告里，看得见。

### B 组 · 技术硬规矩（`AGENTS.md` 第 4 条）

| 代号 | 检查什么 | 为什么 |
| --- | --- | --- |
| **B1** | 没有 `<script type="module">` | `file://` 下模块脚本会被浏览器直接拦掉 → 整页白屏 |
| **B2** | 没有「白名单外」的在线资源 | 断网必须能用；线上也不该依赖第三方存活 |
| **B3** | 没有构建步骤 | 不出现 `package.json` / lock 文件 / `node_modules` —— 双击就要能用 |
| **B4** | 没有 `innerHTML` 拼接 | 内容里有个 `<` 就会让整页错乱；文字只能走 `textContent` |
| **B5** | `localStorage` 只在 `store.js` | 以后换云端只改那一个文件 |
| **B6** | 不用 `toISOString()` 取日期 | 它给的是 UTC，国内晚上 8 点后打的卡会被记到第二天 |
| **B7** | 脚本加载顺序对 | 固定为 `config → db → cloud → rules → store → data → app`，换一个就白屏 |
| **B8** | `assets/` 文件名规范 | 小写 + 连字符 + 不带空格，避免本地路径出问题 |

#### ⚠️ B2 里那个「白名单」是刻意的，不是漏网

`index.html` 里有一个 CDN：云端 SDK（Day 17 加的）。
纯静态 + 零构建，引 npm 包就要多一道构建步骤 —— 所以 SDK 用 CDN 引。
**这个例外写进了白名单**，检查项会放行它、但对**任何第二个外部资源报警**。

> 这一条值得单独记住：**检查项要跟项目真实约定对齐，不能照文档一刀切。**
> 照文档写「禁止一切在线资源」，会对一个正常的项目报红 —— 那叫误报，
> 跟漏报一样会让人不信任这份报告。

### C 组 · 发布前状态

| 代号 | 检查什么 | 怎么算通过 |
| --- | --- | --- |
| **C1** | 线上地址还活着吗 | `HTTP 200` |
| **C2** | 线上跑的是不是本地这份代码 | 逐文件比 md5，**全部一致** |

C2 比对的文件不是写死的清单，而是**从 `index.html` 里引用关系自动推出来的**：
`index.html` + 引用的 `*.css` / `*.js` / `*.svg`（素材类的大文件不比对）。
所以以后新增了 js 文件，它自动进入比对范围，不用改检查脚本。

## 关键实现细节（改的时候别踩）

1. **匹配前必须剥注释。** 项目里的注释大量提到 `innerHTML` / `localStorage` /
   `toISOString`（都是在讲「别用它」）。照着原文匹配必然误报。
   → `.js` 剥掉行注释和块注释，`.html` 剥掉 HTML 注释，**换行保留**（行号才不错位）。
2. **失败必须指到「文件:行号」**，只报「有问题」等于没报。
3. **零子进程。** 在受限环境里 `spawn` 会被挡（`EBUSY`），脚本就会假装检查不了。
   所以文件清单有两条通道：
   - `git ls-files`（权威：只含会被提交的文件）
   - 目录遍历 + 自己解析 `.gitignore`（降级通道，**会包含还没 `git add` 的新文件，更严格**）
   实测过两条通道的清单差异，只有「新建但未 `add` 的文件」这一处，符合预期。

## 故意弄坏验证（2026-10-11，Day 25 实做）

**检查工具最怕的是「永远绿灯」** —— 那样它比没有还糟，因为它给人虚假的安心。
所以第一次做完，必须**故意弄坏**来验它真会红。

| 轮次 | 弄坏哪一项 | 预期 | 实际 |
| --- | --- | --- | --- |
| ① | 在 `assets/config.js` 里塞一行假的 S1 形状凭据 | A1 判失败，指到该行 | 见 `docs/screenshots/day25/` |
| ② | 在 `index.html` 里加一个白名单外的在线字体 | B2 判失败，指到该行 | 同上 |

两轮都**立刻改回原样**，改回后重跑必须恢复全绿 —— 这才叫闭环。

## 加一项新检查，改哪里

在 `check.mjs` 里加一个 `checkXX()`，然后加到文件末尾的 `ALL` 数组里。
三件事要一起想清楚：

1. **怎么算通过**（要有明确判据，不能靠眼看）；
2. **会不会误报**（有没有注释、文档、白名单之类要绕开）；
3. **查不了的时候怎么标**（用「未检查」，不要偷偷算通过）。
